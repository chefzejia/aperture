# 人机协同模型

## 第一性原理

> **Agent 时代，人和 Agent 协同的核心是：双方面对同一个工作状态，共同观测、操作、修正和演化，而不是各自维护一套。**

这条原则适用于任何类型的工作，不限于知识库、投标或某个具体业务。

## 为什么这条原则成立（控制面透明 vs 执行面黑盒）

Agent 写代码和处理信息的速度远超人类，但如果人看不清系统当前的意图、边界和裁判标准，项目一旦跑偏——方向偏、事实偏、边界破——人甚至不知道该给 Agent 下什么指令去纠偏。

今天在真实工程里，哪怕出了 Bug，绝大多数时候人也不会亲自去手改那几百行实现代码，依然是调度 Agent 去修。**我们追求“共同可观测”，从来不是为了让人回去当苦力手改每一行代码，更不是拒绝使用数据库、编译器或三维引擎等底层黑盒；而是为了守住人对系统的「可诊断性」与「可重导向性（Steerability）」。**

因此，必须严格划清**「什么必须对人透明（白盒）」**与**「什么可以彻底交给机器（黑盒）」**：

| 层次 | 包含对象 | 透明度要求 | 第一性原理（为什么） |
| :--- | :--- | :--- | :--- |
| **1. 控制与契约面（方向盘）** | 产品定位、模块职责边界、数据 Schema、工作规则（`PRODUCT` / `ARCHITECTURE` / `SKILL` / `LESSONS`） | **100% 人机共读（白盒）** | 决定“去哪里、什么算对、红线在哪”。若此层成为黑盒，人就丧失了定义目标与纠偏的能力。 |
| **2. 裁判与状态面（仪表盘）** | 当前任务调度板、守卫单测断言、提交验证账本（Git Commit Body）、核心业务真相源 | **100% 人机可核查（白盒）** | 决定“当前在哪、验收是否自欺欺人”。出问题时，人靠这一层在 1 分钟内定位错在哪一层，从而精准指挥新 Agent 重修。 |
| **3. 计算引擎与存储面（发动机）** | 关系/分析数据库（Postgres / SQLite / DuckDB）、渲染与物理引擎（Unity / Unreal）、操作系统原生框架 | **成熟底座黑盒（配透明查询口）** | 封装客观数学与物理复杂度。只要能通过 SQL、CLI 或确定性接口毫秒级查询状态，底座越成熟、越黑盒，系统上限越高。 |
| **4. 局部实现与派生索引面（齿轮）** | 模块内部的具体业务代码、编译产物、全文/向量检索索引、运行期缓存 | **对人半黑盒（按需抽检，坏则重写）** | 当边界（第 1 层）和裁判（第 2 层）被死死焊住后，垂直小包内部的几百行代码怎么写无需人逐行盯防，随时可由 Agent 局部重写或重建。 |

**控制面与裁判面共同可观测，执行面与存储面放心借力黑盒——这是人和 Agent 既能深度协同、又不会被细节拖垮的前提。**

## 共同工作状态的三个层次

### 1. 工作状态本身：记录"这件事是什么"

工作状态是人和 Agent 共同维护、共同可见的事实层。它的形式可以是 Markdown 文件、数据库记录、代码仓库或其他结构，但必须满足：

- 人能直接看到、理解和修改；
- Agent 能读取、引用和操作；
- 重要结论能回到原始来源，可以被核对；
- 未知、冲突和待确认保持显式，不能被伪装成确定。

### 2. 工作规则：记录"应该怎么做"

Skill 和经过确认的长期工作规则，描述步骤、检查项、停止条件、权限边界和输出约束。

工作规则不存事实，也不替代工作状态。规则和事实分离，才能在不修改事实的情况下优化工作方式，也才能在规则变化时知道哪些事实不受影响。

### 3. 当前任务：记录"这一次发生什么"

客户、金额、工期、临时要求、当前草稿和本次交付物，属于当前任务工作区。任务可以引用长期工作状态和规则，但任务变量不能自动写入长期状态。

## 协同边界与人的四个支点（定界 · 造台 · 证伪 · 审美）

人和 Agent 的能力结构不同，协同要从这一差异出发设计，而不是让 Agent 模拟人、或者让人退化成 Agent 的人工审查机器。

**Agent 擅长**：跨语言高频编码、快速处理海量信息、结构化提取、执行确定性步骤、跑全量回归测试。

**人擅长**：在一个项目从 0 到 1 再到长期演进的生命周期里，守住四个机器无法替代的支点：

| 人的四个支点 | 发生阶段与核心职责 | 为什么不能甩给 Agent？ |
| :--- | :--- | :--- |
| **1. 定界（Boundary）** | **立项 0→1 与架构演进**：决定什么借力成熟物理/数学底座、什么剥离为纯逻辑内核；划清稳定核心与高频变化边缘的边界；批准不可逆操作 | Agent 擅长在既定边界内求解，但无法为商业代价、合规风险与长期维护边界负最终责任 |
| **2. 造台（Harness）** | **动手写业务前**：打通“异常直出纯文本、命令行状态自省、一键冒烟脚本”的自动化可观测实验台，提供内存级仿真底座 | 若运行环境对 Agent 是黑盒，Agent 只能靠盲猜堆砌补丁；先造好透明实验台才能释放 Agent 算力 |
| **3. 证伪（Falsification）** | **测试门禁与规则沉淀**：要求关键修复具备“手动破壁必红（`Broken by hand`）”证据；独立验收打回残次品时，把漏检模式记为待验证规则，同一模式累计 3 次（或单次造成严重事故）即固化为静态守卫单测 | 作者 Agent 存在“自我确认”偏见，且容易写出恒真假测试；需要人定义证伪机制与审计账本 |
| **4. 审美（Taste）** | **产品交付与冲突裁定**：在自动化执行与独立验收过滤掉显性工程和交互缺陷之后，站在真实人类用户视角审视交互顺滑度、视觉呼吸感与文案自然度，对产品价值取舍做最终裁决 | 机器脚本绿灯或独立验收初筛不等于最终产品品味；价值取舍与真实感官审美永远属于人 |

**Agent 是高速执行者与发现者，人是定界者、造台者、证伪者与审美裁决者。** 把方向盘推给 Agent，或者让人陷入逐行改代码的苦力，都会破坏协同结构。

## 架构只有一条主线

工作过程中可以有候选、草稿和失败现场，用于回溯和重新运行。这些中间产物不能成为单一事实来源之外的重复维护副本：

- 工作状态是事实基础，索引、缓存和生成结果必须与之一致；
- 辅助工具（搜索索引、向量数据库、生成结果）可以删除后重建，不能独立维护事实；
- 业务可以有过程，架构不需要中间真相。

## Skill：原则在具体工作中的落地

每个核心能力（Skill）是通用协同模型在一类具体工作中的验证和实现。Skill 可以定义自己的工作状态格式、字段、工具、权限和检查项，但不能违反通用原则，也不能把自己的实现方式或特定宿主工具提升为全局要求。

| 维度 | 通用原则 | Skill 自行决定 |
|-----|---------|--------------|
| 工作状态 | 人和 Agent 共同可观测、可操作、可修正 | 格式、字段、目录结构 |
| 工作规则 | Skill 与确认的长期规则 | 业务步骤、审批条件、停止规则 |
| 当前任务 | 独立工作区、可引用、不可自动反写 | 任务变量的具体形式 |
| 辅助工具 | 可重建、不独立维护事实 | 具体工具和触发条件 |

## 判断是否仍在主线上

1. 控制面（契约与边界）和裁判面（任务栈、门禁断言、提交账本）是否对人和 Agent 共同透明？
2. 人能否不读几万行底层实现源码，仅凭控制面与裁判面就在 1 分钟内看清系统状态？
3. 未知、冲突和待确认是否保持显式，没有被伪装成确定结果？
4. 单次任务的临时变量是否与长期工作状态分离？
5. 删除派生索引、缓存和外挂编排框架后，核心契约与业务真相是否仍然完整可用？
6. 当某个 Agent 跑偏或卡死时，人能否不依赖其被污染的聊天上下文，直接换一个新的 Agent 精准接手纠偏（可重导向性）？

如果其中任何一条需要“黑盒中间态”或“重复维护的副本”才能成立，协同结构就已经偏离主线。
