# AI-Native 第一性原理：从代码抽象走向规则抽象

## 核心公理（The AI-Native Razor）

> **前 AI 时代的许多主流框架、水平分层与中间文档，是在“人类手写代码慢、跨语言学习贵、记忆带宽有限”的物理约束下做出的合理工程取舍（Human-Bandwidth Tradeoffs）。**
>
> **当 Agent 将“语法记忆、跨语言转译、底层 API 调用与样板编写”的边际成本大幅压低后，工程设计的重心发生了根本迁移：所谓的代码抽象与厚重兼容层不再那么重要，规则抽象、边界隔离与自动化验证实验台（Harness）变得至关重要。我们应当主动审视旧惯性——借力真正的物理与数学底层引擎，剥离阻碍可观测性的妥协胶水。**

---

## 一、 选型公式的根本逆转

### 1. 前 AI 时代的选型公式（受限于人脑与手速）
$$\text{传统选型} = \text{物理/数学最优解} - \text{人类手写成本与学习门槛}$$

因为人类手算坐标慢、同时掌握多门原生语言难、手写底层 SQL 容易晕，行业被迫发明了大量“二道贩子”式的中间层：
- 画不出精密矢量图 $\rightarrow$ 用静态位图（PNG）或拿 HTML `div` 盒子硬凑，或者引入几兆字节的黑盒图表库（ECharts）；
- 不想同时写 Swift 和 Kotlin $\rightarrow$ 引入厚重的跨端运行时桥接层（React Native / Electron），牺牲原生帧率与系统级交互；
- 怕写复杂 SQL 窗口函数 $\rightarrow$ 套一层厚重的 ORM，在应用内存里跑出 N+1 查询；
- 怕写胶水代码 $\rightarrow$ 在可视化画布上拖拽几十个框框连线（No-Code / Low-Code），丧失版本控制与可测试性。

### 2. AI-Native 时代的选型公式（回归物理与数学上限）
$$\text{AI-Native 选型} = \text{物理/数学/系统原生最优解} \times \text{形式化确定性（Schema / 编译器 / 坐标系）}$$

当写代码的执行者变成 Agent 时，**出现了极具爆发力的正反馈**：
- **越是接近底层物理、数学定义越严格、编译期检查越苛刻的技术**（如 SVG 笛卡尔坐标、Swift/Rust/TypeScript 强类型编译器、Svelte 编译期响应式、DuckDB/Polars 关系代数），**确定性信号越清晰，Agent 反而写得越准、越快、越没有幻觉！**
- 反之，那些为了照顾人类“少写几行字”而发明的黑盒封装、隐式魔法、动态松散语法和拖拽式工具，反而成了阻挡 Agent 视线、拉低产品物理上限的枷锁。

### 3. 人机注意力守恒与“状态去 Session 化”（Attention Conservation & Sessionless State）
$$\text{系统有效吞吐量} = \frac{\text{近乎无限的 Agent 并发算力}}{\text{极度稀缺的人类注意力带宽（3\sim 5 个并发焦点上限）}}$$

当算力不再稀缺后，**人类注意力成了整个系统唯一的物理瓶颈**。每一条消息、每一次窗口切换、每一个需要人盯着的会话（Session）都在消耗注意力。因此必须遵循三条推论：
1. **默认单焦点汇聚（Single Human Entrypoint）**：人类永远只面对唯一的主控入口（一个主会话或一张任务单），所有跨角色任务路由、后台执行与视觉验收均由编排层在幕后自动闭环，仅在需要做价值裁定或交付最终成果时才消耗人的注意力。
2. **领域状态去 Session 化（Sessionless State）**：项目的目标、架构契约与任务状态必须 100% 落盘于工作区文件与 Git 历史中，绝不绑死在某段易腐的聊天记录（Chat Session）里。
3. **执行节点热驻留（Warm Compute Reuse）**：状态是无会话的，但执行计算的会话应在同一项目周期内保持常驻，复用已加载的上下文与提示缓存，减少冷启动重读的成本。

## 二、 六大领域的“去妥协层”对照表（物理特性要求 vs 默认参考栈）

为保持通用原则与具体项目场景解耦，下表先定义**跨场景成立的物理/数学特性要求**，再给出**新建同类项目且无既有历史栈约束时的默认参考实现（Default Reference Stack）**：

| 维度 | 旧时代的“人类带宽妥协层”（果断质疑并砍掉） | AI-Native 物理/数学特性要求（通用原则） | 新项目默认参考栈（场景匹配时首选） | 为什么在 AI 时代全面胜出？ |
| :--- | :--- | :--- | :--- | :--- |
| **1. 视觉与空间表达** | PNG 死图 / HTML `div` 盒子硬凑空间关系 / 巨型黑盒图表库 | **显式二维笛卡尔坐标系矢量图 + 零虚拟 DOM 编译期响应式绑定** | 声明式内联 `<svg viewBox>` + `Svelte 5 (Runes)` | LLM 对显式二维坐标 $(x, y)$ 的解析几何计算远准于隐式 CSS 盒模型盲猜；无限缩放、零包体累赘、原型可 1:1 零失真转生产。 |
| **2. 终端与跨平台** | 共享臃肿运行时桥接层（Electron / RN 等） | **交互与表现层共享规则契约、各端原生展开；高精度确定性算法内核通过二进制（FFI / C-ABI）物理共享** | 表现层：`PRODUCT.md` + 设计 Token $\rightarrow$ `Swift/SwiftUI` / `C# WinUI 3` / `Svelte 5`；算法核：`Rust/C/纯逻辑库` | UI 强耦合宿主 OS，AI 跨语言转译成本趋近于 0，各写原生直接拿满帧率与系统级交互；而联机帧同步、加密或离线引擎等需 bit-for-bit 一致的数学内核则通过二进制库共享。 |
| **3. 依赖、分包与组件组装** | 为 5% 功能引入黑盒依赖包 / `service/util/handler` 水平分层大泥球 / 代码生成与反射 DI 容器（如 `wire`/`fx`/IoC） | **可离线仿真的纯逻辑内核（Functional Core）+ 垂直高内聚小包（单向无环 DAG）+ 入口显式构造函数组装** | 核心规则零外部 I/O 依赖；按业务领域或物理机制切分小包；`main` 显式传参组装；100~200 行零依赖纯函数 | 水平分层导致单包数百文件命名空间裸奔与上下文碎片化；DI 容器掩盖 >10 个依赖的上帝对象。纯逻辑内核 + 垂直小包让 90% 代码可在内存仿真底座上毫秒级自测，零内部 Mock。 |
| **4. 数据计算与存储** | 厚重黑盒 ORM + 未经验证的过早分布式拆分 | **关系代数 / 向量化矩阵计算 + 匹配业务规模的成熟事务底座** | 单机/内嵌：`SQLite WAL` / `DuckDB + Polars`；多租户云：`Postgres + Redis`（配显式 SQL / `sqlc`） | 关系代数与矩阵向量化是数学上最清晰的数据变换语言；去掉重型 ORM 的隐式映射损耗，单机或云端均保持高可观测性与确定性查询性能。 |
| **5. 类型与语言防线** | 动态弱类型“先跑起来再说” / 靠人工 Review 抓低级错 | **端到端单一强类型 Schema 真源 + 严苛静态编译器** | `Pydantic v2` $\rightarrow$ `OpenAPI` $\rightarrow$ `TS Strict` / `Swift` / `Rust` | 严苛的编译器对人是负担，对 Agent 却是**毫秒级、零成本的确定性强化学习反馈信号**，将 90% 集成错误消灭在编译期。 |
| **6. 流程与编排文档** | 长链条传话筒文档（PRD $\rightarrow$ RFC $\rightarrow$ Figma $\rightarrow$ 接口文档） + 拖拽连线低代码 | **单一产品定义 + 原型即生产 + 代码即工作流（Code-as-Workflow）** | 单份 `docs/PRODUCT.md` + 可运行原型 + 强类型 Agent 校验函数 | 砍掉一切不能被编译器或运行时直接消费的中间二道贩子；用强类型代码和可运行原型作为人机唯一的共同工作状态。 |

## 三、 每次动手前的“第一性原理三问”（The 3-Question Interrogation）

在开启新项目、设计新功能、引入外部库或沿用旧习惯前，Agent 与人必须共同用以下三个问题做一次审视：

1. **质疑妥协性（Why does this exist?）**：
   > “我们正准备用的这个框架/库/流程，到底是因为它在**物理性能和最终体验上最好**，还是仅仅因为**以前人类手写太慢、学不会原生方案而找的替代拐杖**？”
2. **探寻原生解（What is the mathematical/native ideal?）**：
   > “如果完全不考虑‘人手敲代码累不累、算数学坐标烦不烦’，这个问题在**底层系统、数学几何或关系代数上最纯粹、最直接的原生解法**是什么？（如：直接写 `<svg>`、直接写 Swift、直接写 150 行零依赖算法、直接用 DuckDB）”
3. **验证可观测与确定性（Is it deterministic for AI?）**：
   > “这个方案是把状态藏在黑盒配置和隐式副作用里，还是暴露为**显式的数学坐标、纯函数变换和强类型编译器契约**？”

**判断准则**：优先解决真实业务问题（“抢不到票，客户端再顺也没用”）；在此前提下，只要更贴近底层原语、边界更干净的方案能由 AI 在可接受成本内生成并通过验证，就不再沿用旧时代臃肿的兼容胶水。

## 四、 反教条与跨领域反证门禁（Falsification & Anti-Dogma Boundaries）

任何工程规则一旦脱离物理前提就会退化为新的盲目教条。在应用上述原则或向本仓库新增规则前，必须通过以下三条边界反证：

1. **区分「真物理/数学领域引擎（必须借力）」与「人类带宽妥协胶水（果断砍掉）」**：
   - **去妥协层 $\neq$ 盲目手搓底层引擎**。凡是封装客观物理、硬件加速或数学复杂度的**领域底座**（如 3D 渲染与物理引擎 Unity/Unreal、ACID 事务与列式计算引擎 SQLite/Postgres/DuckDB、音视频编解码 FFmpeg、操作系统原生 UI 框架 SwiftUI/WinUI 3），必须全力借力；
   - 我们无情砍掉的只是**横亘在人与领域底座之间的二道贩子胶水**（如阻碍 Git diff 与 AI 读写的二进制蓝图面条、牺牲帧率的跨端套壳桥接、掩盖 SQL 的重型 ORM、掩盖上帝对象的 DI 容器）。
2. **区分「低频控制面（纯文本管道）」与「高频数据面（零拷贝/同内存空间）」**：
   - 在低频控制流（$<100\text{ Hz}$ 的配置下发、CLI 协同、跨语言工具调用）中，不同语言与模块间优先通过**纯文本、JSON 或字节流**通信，保持最高可观测性；
   - 但在高频热路径（如 $60\sim 120\text{ FPS}$ 的游戏主循环、实时音视频流、高频行情矩阵计算）中，严禁在热循环内做跨进程文本序列化，必须留在同一内存空间或通过零拷贝（Shared Memory / C-ABI）传输。
3. **规则准入的跨领域反证测试（Cross-Domain Falsification Gate）**：
   - 切勿每读一篇文章就把某领域的局部套路塞入全局工作流。只有同时在 **系统基础设施、商业 Web/客户端、游戏/高频引擎** 三个场景下反证均成立的规律（如“纯逻辑内核剥离重型 I/O”、“先建自动化可观测实验台再写业务”、“二进制资产退居薄壳、核心状态机保持纯文本”），才能升格为 `docs/core/` 的底层公理；受特定场景约束的方案只归入默认参考栈，并显式标明失效边界。
