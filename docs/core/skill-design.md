# Skill 设计规范

## Skill 是什么

Skill 是围绕共同工作状态运行的一组可复用工作规则和资源。它告诉 Agent：

- 什么时候适用、不适用于什么；
- 需要哪些输入与前置条件；
- 应该按什么步骤工作；
- 什么结果才算完成；
- 遇到什么情况必须停下来交给人。

Skill 负责回答“这件事应该怎么做”。共同工作状态（例如代码仓库中的契约文档、调度板与验收台账，或知识库中的 Markdown 笔记与附件证据）负责回答“这件事现在是什么”。二者可以互相引用，但不能互相替代。

## 规则、工作状态与当前任务的边界

- **共同工作状态**：记录事实、目标契约、关系、验证证据与当前状态（如软件仓库中的 `ARCHITECTURE.md` / `TASKS.md` / `FEATURES.md` 与代码本身，或知识库笔记的正文、Frontmatter、Wiki 链接与附件引用）。
- **工作规则层**：Skill 和经过用户确认的长期工作规则，记录步骤、检查项、停止条件、权限边界和输出约束。
- **当前任务工作区**：记录单次任务的临时输入、草稿、中间现场、客户/金额/工期等临时变量和本次交付物。

不要把特定项目的业务事实写进通用 Skill，也不要把“应该如何工作”塞进事实对象本身（例如每篇知识笔记的 Frontmatter），更不要把单次任务的临时变量自动写入长期状态。

## 一个 Skill 的组成与自封闭契约

一个 Skill 是一个独立的目录，必须包含 `SKILL.md`，其余子目录按需建立：

```text
skill-name/
├── SKILL.md              # 必需：元数据和可执行核心流程、红线与检查清单
├── references/           # 可选：设计原理、取舍推导与参考实现
├── scripts/              # 可选：必须精确重复的确定性操作
└── assets/               # 可选：供目标项目实例化的纯净模板（*.template.md）
```

一个只有 `SKILL.md` 的 Skill 可以成立。为了凑结构建立空目录，只会增加认知成本。

- **目录 100% 自封闭**：每个 Skill 目录是独立的分发与加载单元，内部文件（`SKILL.md`、`references/`、`assets/`）的相对链接必须封闭在该 Skill 目录自身之内，不依赖外层仓库的父级路径。
- **正文轻执行、原理进 `references/`**：`SKILL.md` 只保留可执行步骤、红线、停止条件与验收清单；大段“为什么这样设计”的推导与实证下沉到 `references/`，避免稀释 Agent 执行时的注意力。
- **模板命名防误加载**：`assets/` 下供项目实例化的模板统一使用 `*.template.md` 命名，禁止直接命名为 `AGENTS.md` 或 `CLAUDE.md`，防止被 Agent 宿主自动加载为当前仓库规则。
- **跨 Skill 单一事实来源与模板自足**：不同 Skill 之间可按名称指路委托细则，不跨 Skill 复制同一套流程以免改一处漏多处；若某份模板是特定角色运行时唯一读取的文件（例如后台总控读取的角色契约），则该模板必须保持自足并与 `SKILL.md` 严格同步。

## `SKILL.md` 应该写什么

顶部 YAML Frontmatter 至少包含以下字段：

```yaml
---
name: skill-name
version: 1.0.0
description: >
  做什么。
  什么时候使用。
  不适用于什么。
---
```

其中 `name` 与目录名一致，`version` 与仓库统一发布版本保持同步。正文使用现在时态陈述适用范围、核心流程、输入、输出、检查和停止规则；确定性检查交给脚本或守卫测试，不把特定宿主客户端的私有行为、CLI 细节或模型型号写死成全局协议。

## 从真实任务与情景回放迭代

Skill 应从反复出现的真实工作中长出来，并用可重复的回放验证每次修改：

1. 选一项真实任务（或真实翻车案例）；
2. 让 Agent 按当前 Skill 执行；
3. 检查用户真正需要的结果；
4. 区分规则不清、执行错误和规则本身不对；
5. 只修改能解释这个问题的部分；
6. 用情景回放（在全新会话中加载改动前后的 `SKILL.md` 或自足模板并逐条比对评分标准）确认新规则生效且既有规则未退步。

迭代的是工作规则，不是共同工作状态的底层原则。无论 Skill 怎样改，控制面与裁判面仍保持对人和 Agent 共同透明、可核查、可随时换新会话接管。

## 失败安全

任何会读取、整理或写入共同工作状态的 Skill，都应该做到：

- 不覆盖、不删除**不受版本控制的外部原始材料**（如知识库 `inbox/` 原件、用户真实生产数据），也不擅自清空或回滚**工作区中他人或先前会话留下的未提交修改（Uncommitted / Untracked Work）**；仅针对本次授权修改的已提交 Git 源码及明确声明可随时重置的专用测试沙盒直接原地修改，不制造 `_backup` 防御性副本；
- 保留候选结果和失败现场（在知识库整理中留存 `inbox/` 候选；在代码仓库中通过 Git diff、提交记录与测试日志体现，不在源码或构建目录中堆砌 `_backup` 文件）；
- 重复执行不会无止境地产生重复结果；
- 失败时报告失败步骤、原因和当前状态；
- 只修改明确授权的范围；
- 不把候选、待确认或过期内容当作正式结果；
- 高级索引、缓存、构建产物和测试沙盒可以随时直接覆盖、重建或删除。

## 场景化而不是分叉

通用 Skill 只保留跨场景成立的边界和工作循环。具体业务场景可以补充目录、字段、权限、审批、业务步骤和领域术语，但不得另建一套与共同工作状态互相竞争的事实架构。

例如，软件工程仓库可以在项目契约层定义自己的分层与验证命令，企业投标知识库可以要求证书有效期和项目隔离，个人研究可以更重视隐私和阅读路径。它们共享同一套“控制面透明、状态落盘、规则与事实分离”的基础，只在项目契约与任务层做差异化。

## 一句话判断

> 好 Skill 让 Agent 在一类真实工作中更稳定、更容易检查、更容易失败后接管；它规定工作方法，不把一个场景的习惯或特定宿主的配置伪装成全局基础设施，也不把事实藏到共同工作状态之外。
