# 三角色协作设计

**事实核查**：2026-10-15（基于 Orca 官方推荐 + 第一性原理推导）

> **状态：已被取代。** 本文的三角色方案已演进为 multi-agent-collab Skill 的双环协作（增加了无人值守的 Router 与按需派生的 Auditor，交接文件从 `HANDOFF.md` 改为 `TASKS.md`），现行协议见 [multi-agent-collab](../../skills/multi-agent-collab/SKILL.md)。本文保留为历史记录。

## 设计原则

**角色边界成立的唯一依据**：合并它会产生一个可以说出名字的具体失败。

**模型强度的边界**：
- 能力差异不是拆分理由（同一强模型既能规划又能写码又能审查）
- 信息差异才是拆分理由（Worker 的"我为什么这么写"让他看不见"这么写对不对"）

## 三角色定义

### Brain（协调者 + 架构师）
**会话名**：`brain`

**为什么 Brain 和 Architect 必须合一**：
- 两者需要同一份上下文（项目目标、边界、当前状态、架构决策）
- 两者产出同一类产物（决策和任务分配）
- 在项目唯一的场景下，项目级上下文 = 架构上下文
- 拆分只会增加一次"互相转述"的成本，没有任何隔离收益

**职责**：
- 接收用户需求，理解业务目标
- 制定技术方案、模块边界、接口契约
- 制定任务包（给 Worker）
- 制定验收标准（给 Tester）
- 协调 Worker 和 Tester 的工作流
- 维护 `docs/HANDOFF.md`（当前状态、下一步、阻塞）
- 维护 `docs/ARCHITECTURE.md`（架构决策）
- 处理 Tester 升级的问题（重新制定契约）

**上下文**：
- 用户目标和业务需求
- 架构决策和模块边界
- 当前各 Worker 的状态
- 历史失败模式（LESSONS.md）

**不做**：
- 不写具体实现代码（委托给 Worker）
- 不执行测试（委托给 Tester）

**任务包格式**：
```markdown
# Task: 实现用户认证模块

## 范围
文件：src/auth/
接口：见 docs/api/auth.md
依赖：src/db/user-repo.ts（只读）

## 契约
- 输入：username + password
- 输出：JWT token or error
- 错误处理：3次失败锁定账户
- 性能：登录 < 500ms（P95）

## 实现要求
- 写单元测试（正常、密码错误、账户不存在、锁定）
- 单元测试全部通过后提交

## 验收标准（Tester 执行）
- [ ] 代码符合契约
- [ ] 安全检查：密码不落日志
- [ ] 集成测试：与数据库交互正常
- [ ] 部署测试：生产环境能成功登录

## 不在范围内
- 注册功能（另一个任务）
- OAuth（V2）
```

### Worker（实现者）
**会话名**：`worker-<模块名>`（如 `worker-auth`）

**职责**：
- 读取 Brain 的任务包
- 实现功能代码
- 写单元测试（快速自反馈）
- 运行单元测试验证
- 提交代码给 Tester

**上下文**：
- 当前任务包的范围和契约
- 当前模块的代码
- 为什么这么实现的思路（这是 Worker 独有的上下文）

**不做**：
- 不跨模块修改
- 不做验收判断（单元测试通过 ≠ 验收通过）
- 不做架构决策

**完成标准**：
- 单元测试全部通过
- 代码实现了任务包的契约
- 发送 `worker_done` 给 Brain

---

### Tester（验收者）
**会话名**：`tester`

**为什么 Tester 和 Reviewer 必须合一**：
- 两者需要同一份上下文（契约 + 代码）
- 两者产出同一个产物（通过/不通过的结论）
- 代码审查和测试执行是同一个验收流程的两个**阶段**，不是两个角色
- 拆分会导致 Reviewer 的"代码有问题"和 Tester 的"跑不通"需要协调，增加成本

**为什么 Tester 不能合并到 Worker**：
- **作者给自己发合格证** — 验证退化成自我确认
- Worker 的上下文包含"我为什么这么写"，这个信息本身让他看不见"这么写对不对"
- 这是信息差异，不是能力差异，模型再强也解决不了

**职责**：
- 独立读取代码、任务包、验收标准
- **阶段 1：静态审查**（代码审查）
  - 正确性：逻辑是否符合契约
  - 安全性：是否有注入、泄露风险
  - 边界：是否超出任务包范围
- **阶段 2：动态验证**（测试执行）
  - 集成测试：跨模块交互是否正常
  - 部署测试：直接部署到生产，验证关键路径
- 判断问题严重程度
- 输出验收报告

**单元测试 vs 验收测试**：
- **单元测试**：Worker 写，Worker 自己跑，目的是快速反馈，不是合格证
- **验收测试**：Tester 执行，目的是判断"能不能上线"，是合格证

**判断边界**：
- ✅ **通过** → 通知 Brain "可上线"
- ❌ **实现问题** → 告诉 Brain 哪里需要修复，Brain 重新启动 Worker
- ⚠️ **契约问题** → 升级给 Brain（契约定义错了或冲突了，不是 Worker 的问题）

**验收报告格式**：
```markdown
# 验收报告：用户认证模块

## 结论
❌ 实现问题（需要修复）

## 静态审查
✅ 逻辑正确
✅ 边界清晰
❌ 安全问题：密码错误日志中包含了用户输入（src/auth/login.ts:45）

## 动态验证
⚠️ 未执行（等待修复后再测）

## 必须修复
1. 移除日志中的用户输入，只记录"密码错误"
   位置：src/auth/login.ts:45

## 升级给 Brain
无
```

## 工作流设计

### 标准流程（Brain 自动化协调）

```
用户需求
    ↓
[Brain] 理解需求，制定方案和任务包
    ↓
[Brain] 启动 Worker
    ↓
[Worker] 实现 + 单元测试 → worker_done
    ↓
[Brain] 启动 Tester
    ↓
[Tester] 静态审查 + 动态验证
    ↓
   ┌─── ✅ 通过 ────→ [Brain] 完成，通知用户
   │
   ├─── ❌ 实现问题 ─→ [Brain] 重新启动 Worker（附上反馈）
   │                        ↓
   │                   [Worker] 修复 → worker_done
   │                        ↓
   │                   [Brain] 重新启动 Tester
   │                        ↓
   │                   （循环直到通过或连续失败 3 次）
   │
   └─── ⚠️ 契约问题 ─→ [Brain] 自己重新制定契约和任务包
                             ↓
                        [Brain] 重新启动 Worker
```

**关键**：循环是 Brain 的控制流，不在 Tester 或 Worker 内部。

### 升级路径

```
Worker → Tester → Brain → 人
```

- Worker 遇到不清楚的边界 → 通过 Tester 反馈 → Brain 明确边界
- Tester 发现契约冲突 → 直接升级 Brain → Brain 重新制定
- Brain 遇到架构权衡 → 唤醒人做决策

### 适配"直接上线部署调试"

**Tester 的动态验证阶段**：
1. 静态审查通过后，直接部署到生产
2. 执行关键路径验证（登录、支付等核心功能）
3. 监控错误日志（5-10 分钟）
4. 如果生产验证通过 → 报告"✅ 通过"
5. 如果生产出现问题 → 报告"❌ 实现问题"或"⚠️ 契约问题"

**优点**：
- 省略本地模拟环境（直接用真实用户数据调试）
- 加快发布节奏（一次性完成测试+部署）
- 符合"用户量小，允许快速迭代"的场景

**风险控制**：
- Tester 必须先通过静态审查（不能盲目部署）
- 部署后立即验证关键路径
- 有错误立即回滚或标记为"实现问题"

## Orca 协作协议实现

### Brain 的协调脚本（实际 Orca CLI）

```bash
#!/bin/bash
# Brain 的核心协调循环
# 基于 Orca v1.4.224 实测 CLI

ORCA=/Applications/Orca.app/Contents/Resources/bin/orca
OBJECTIVE="$1"  # 用户需求

echo "=== Brain: 理解需求并制定方案 ==="
echo "需求：$OBJECTIVE"
echo ""

# Brain 自己制定方案和任务包（不需要另一个 Architect agent）
# 这部分是 Brain 在自己的会话中完成的，不是调用 worker-start
echo "请 Brain 制定技术方案和任务包..."
echo "（在 Brain 的会话中完成，生成任务包）"
echo ""
read -p "任务包已制定，按回车继续..." dummy

# 1. 创建 Run（命名空间和消息中心）
echo "=== 创建 Run ==="
RUN_ID=$($ORCA orchestration run-create --objective "$OBJECTIVE" --json | jq -r '.run_id')
echo "Run ID: $RUN_ID"
echo ""

# 2. 启动 Worker（实现阶段）
echo "=== 启动 Worker ==="
TASK_PACKAGE_FILE="task-package.md"  # Brain 写好的任务包
if [ ! -f "$TASK_PACKAGE_FILE" ]; then
  echo "错误：未找到任务包文件 $TASK_PACKAGE_FILE"
  exit 1
fi

TASK_PACKAGE=$(cat "$TASK_PACKAGE_FILE")

$ORCA orchestration worker-start \
  --run "$RUN_ID" \
  --spec "$TASK_PACKAGE" \
  --agent codex \
  --model "claude-sonnet-4" \
  --worktree current \
  --task-title "Implementation" \
  --json

# 3. 等待 Worker 完成
echo "等待 Worker 完成..."
WORKER_MSG=$($ORCA orchestration check --run "$RUN_ID" --wait --types "worker_done" --timeout-ms 900000 --json)
echo "Worker 已完成"
echo ""

# 4. 确认消息（ACK）
DELIVERY_ID=$($ORCA orchestration check --run "$RUN_ID" --json | jq -r '.delivery_id')
$ORCA orchestration check --run "$RUN_ID" --ack "$DELIVERY_ID" --json

# 5. 循环：Tester 验收（最多 3 次重试）
MAX_RETRY=3
RETRY_COUNT=0

while [ $RETRY_COUNT -lt $MAX_RETRY ]; do
  echo "=== 启动 Tester（第 $((RETRY_COUNT+1)) 次验收）==="
  
  # 启动 Tester
  $ORCA orchestration worker-start \
    --run "$RUN_ID" \
    --spec "验收任务：

任务包：
$TASK_PACKAGE

请执行：
1. 静态审查（代码审查）
2. 动态验证（集成测试 + 部署测试）
3. 输出验收报告" \
    --agent codex \
    --model "claude-sonnet-4" \
    --worktree current \
    --task-title "Testing & Acceptance" \
    --json
  
  # 等待 Tester 完成
  echo "等待 Tester 完成..."
  TESTER_MSG=$($ORCA orchestration check --run "$RUN_ID" --wait --types "worker_done,escalation" --timeout-ms 900000 --json)
  echo ""
  
  # 判断结果
  MSG_TYPE=$(echo "$TESTER_MSG" | jq -r '.messages[0].type')
  
  if [ "$MSG_TYPE" = "worker_done" ]; then
    OUTCOME=$(echo "$TESTER_MSG" | jq -r '.messages[0].outcome')
    REPORT=$(echo "$TESTER_MSG" | jq -r '.messages[0].body')
    
    echo "=========================================="
    echo "验收报告："
    echo "$REPORT"
    echo "=========================================="
    echo ""
    
    if [ "$OUTCOME" = "succeeded" ]; then
      echo "✅ 验收通过，任务完成"
      break
    else
      echo "❌ 需要修复（第 $((RETRY_COUNT+1)) 次重试）"
      RETRY_COUNT=$((RETRY_COUNT+1))
      
      # 确认消息
      DELIVERY_ID=$($ORCA orchestration check --run "$RUN_ID" --json | jq -r '.delivery_id')
      $ORCA orchestration check --run "$RUN_ID" --ack "$DELIVERY_ID" --json
      
      if [ $RETRY_COUNT -ge $MAX_RETRY ]; then
        echo "❌ 连续失败 $MAX_RETRY 次，可能是契约问题，需要 Brain 重新制定"
        break
      fi
      
      # 重新启动 Worker，传递反馈
      echo "重新启动 Worker 修复问题..."
      $ORCA orchestration worker-start \
        --run "$RUN_ID" \
        --spec "$TASK_PACKAGE

修复以下问题：
$REPORT" \
        --agent codex \
        --model "claude-sonnet-4" \
        --worktree current \
        --task-title "Fix Issues" \
        --json
      
      # 等待 Worker 完成
      WORKER_MSG=$($ORCA orchestration check --run "$RUN_ID" --wait --types "worker_done" --timeout-ms 900000 --json)
      
      # 确认消息
      DELIVERY_ID=$($ORCA orchestration check --run "$RUN_ID" --json | jq -r '.delivery_id')
      $ORCA orchestration check --run "$RUN_ID" --ack "$DELIVERY_ID" --json
    fi
  elif [ "$MSG_TYPE" = "escalation" ]; then
    echo "⚠️ Tester 升级问题，契约可能有问题"
    
    ESCALATION_REASON=$(echo "$TESTER_MSG" | jq -r '.messages[0].body')
    echo "升级原因：$ESCALATION_REASON"
    echo ""
    echo "需要 Brain 重新制定契约和任务包"
    
    exit 1
  fi
done

if [ $RETRY_COUNT -eq $MAX_RETRY ]; then
  echo "❌ 连续失败 3 次，任务失败"
  echo "可能是契约问题，建议 Brain 重新制定"
  exit 1
fi

echo ""
echo "✅ 任务完成"
```

**关键设计**：
- Brain 不是通过 `worker-start` 启动另一个 agent 来规划，而是在自己的会话中完成规划
- 任务包写入文件（如 `task-package.md`），脚本读取后传递给 Worker
- Brain 通过读取 Tester 的报告，判断是"实现问题"还是"契约问题"
- 连续失败 3 次时，Brain 知道该重新制定契约了

## 项目文档组织

```

├── AGENTS.md              ← 入口：声明采用三角色协作
├── README.md              ← 安装和运行入口

    ├── ROLES.md           ← 定义 brain/worker/tester
```

## 你只需要做的事

### 1. 与 Brain 交互

**你的日常工作**：
```
你：实现用户认证功能
  ↓
Brain：理解需求，制定方案...（Brain 自己完成，不启动另一个 agent）
Brain：方案已制定，是否批准？[查看方案和任务包]
  ↓
你：批准
  ↓
Brain：已启动 Worker 实现...
Brain：Worker 完成，已启动 Tester...
Brain：Tester 报告需要修复 [查看报告]
Brain：已重新启动 Worker 修复...
Brain：Tester 报告通过，已部署到生产 ✅
  ↓
你：好的（任务完成）
```

**你只需要**：
- 提需求给 Brain
- 必要时审批 Brain 的方案
- 必要时审查 Tester 的报告（连续失败时）
- 其他全部自动化

### 2. Brain 的两种工作模式

**模式 A：Brain 自己规划**（推荐）
- Brain 在自己的会话中理解需求、制定方案、编写任务包
- 任务包保存为文件（如 `task-package.md`）
- 协调脚本读取任务包，启动 Worker

**模式 B：Brain 调用协调脚本**
- Brain 编写任务包
- Brain 调用 `brain-coordinate.sh <需求>`
- 脚本自动处理 Worker/Tester 循环
- 脚本结束后 Brain 读取结果

两种模式都是 Brain 自己规划，区别只在于"循环控制"是在 Brain 的会话里还是在脚本里。

## 关键优势

1. **职责内聚**
   - Brain：规划 + 协调（同一份上下文，同一类产物）
   - Worker：实现 + 自测（作者的视角）
   - Tester：审查 + 验收（独立的视角）

2. **必要拆分**
   - Worker/Tester：唯一一条模型强度无法溶解的边界（信息差异，不是能力差异）
   - 其他拆分都会增加成本而无收益

3. **适配你的需求**
   - 只与 Brain 交互
   - Brain 常驻可见
   - Tester 常驻可见
   - Worker 可临时
   - 项目唯一 → Brain = Architect

4. **利用 Orca 基础设施**
   - 不需要自己实现消息队列
   - orchestration.db 自动持久化状态
   - 支持 `--model` 选择模型
