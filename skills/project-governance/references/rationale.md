# 项目治理设计原理

## 为什么拒绝“跨仓复制大段静态标准”

在 Agent 时代，治理文档面临两个物理约束：

1. **注意力稀释（Context Dilution）**：每次会话让 Agent 先读几百行的通用软件工程教导，会严重稀释当前项目核心红线与业务契约的权重。
2. **副本腐败（Copy Drift）**：把通用标准复制到十个业务仓库，就制造了十份需要同步的静态副本，违背“单一事实来源”的第一性原理。

因此：
- **通用工程素养与工作方法**（如如何调试、如何写测试、如何做多 Agent 协作）应当封装为独立的 **Skills**（如 `engineering-discipline`、`multi-agent-collab`），按任务性质由 Agent 动态加载。
- **项目仓库内的文档**只记录**属于这个项目自己的事实与边界**（定位、架构契约、验证命令、踩坑记录）。

## 为什么是“代码门禁管生死 + 薄契约管边界”，而非“零文档”或“长篇文档”？

在高频 Agent 开发的仓库（如日均百次提交的 `magpie` 与 `deepseek-harness`）中，存在一个反直觉的平衡点：

1. **为什么不能靠文档叮嘱规则？（能写单测门禁的绝不写文档）**：
   - 写在 Markdown 里的“禁止跨模块引用”、“禁止裸调 `exec.Command`”三个月后必然腐烂或被子 Agent 忽略。
   - 凡是可机械校验的不变量，必须直接写成 `tests/` 下的**架构守卫单测（Guard Test）**或 CI 门禁。代码改错，测试立红。
2. **为什么又不能“完全零文档”？（为未来子 Agent 省 Token 与防误改）**：
   - 源码只能表达“当前怎么运行”，表达不出**“哪些是故意设计的负向保证（Negative Guarantees）、哪些是淘汰过的诱人陷阱（Why not X）”**。如果完全零文档，新启动的 Worker Agent 每次都要通读数千行源码去猜意图，甚至把你特意设计的防御逻辑当成 Bug“顺手优化”掉。
   - **薄契约（Thin Reference）黄金法则**：
     - **只链接源码符号，不抄录常变细节**：写明“由 `internal/provider/migrate.go` 中的 `retiredBuiltins` 控制”，绝不把具体列表抄在文档里；
     - **内部重构零文档税**：只要子系统对外职责、状态流转和失败契约未变，内部重构不需要改一个字的文档；
     - **现在时态 & 零心路历程**：已合入的文档只用现在时陈述当前契约，严禁保留推理过程（Reasoning Transcripts）、验收打勾清单或 `"（已实现！）"` 等易腐标注。

## 稳定契约 vs 动态状态（两级任务漏斗 + 给 `TASKS.md` 彻底减重 + Commit Body 留痕）

项目文档按生命周期分为两类，绝不混写：

| 类型 | 包含文档 | 更新频率与方式 |
| --- | --- | --- |
| **稳定契约** | `README.md`, `AGENTS.md`, `PRODUCT.md`, `ARCHITECTURE.md`, `DEPLOYMENT.md` | 仅当对外承诺、模块边界、公共接口或部署流程改变时，随代码在**同一个 Commit** 中更新。 |
| **动态状态** | `LESSONS.md`, `TASKS.md`（单 Agent 按需临时建 / 双环协作作常驻轻量滑动调度板） | **海量外部 Issues/PR 先在仓外（GitHub Issues 或 `.tmp/triage/`）完成去重聚类，仅近期立项执行的活跃任务进入 `docs/TASKS.md`（始终只留未结案区块 + 最近 1~2 个已结案锚点）**。严禁在 `TASKS.md` 中堆砌历史验收大表，单次修改的根因与验证证据按需写入 **Git Commit Body**。 |

## 为什么砍掉中间态（RFC / 多份领域碎文档 / 文字版 DESIGN.md）

传统大团队研发流程依赖长链条的文字缓冲物（`PRD → DOMAIN → RFC → Figma/DESIGN.md → 接口文档 → 代码`），因为在人类组织中跨部门沟通昂贵、改代码慢。

但在 **高杠杆个体/小团队 + Agent 协同（AI-Native）** 模式下，写代码和改原型的速度已经远快于维护多份中间文档。保留长链条会带来严重的**上下文跳转损耗**与**契约撕裂**：

1. **一份 `docs/PRODUCT.md` + Directory-as-Product**：
   - 把产品定位、核心模块、交互铁律、明确不做什么（Non-goals）和核心领域术语内聚在一份 `docs/PRODUCT.md` 中，避免 Agent 为了改一个字段去跨 5 份碎文档（`PRODUCT` / `DOMAIN` / `DATA_PROTOCOL` / `TERMS`）对齐。
   - 前后端代码目录直接 1:1 映射 `PRODUCT.md` 中的顶层模块名（例如产品分 4 个 Tab，后端包与前端页面目录就叫这 4 个名字），让人和 Agent 零翻译成本定位代码。
2. **讨论完直接落决策（ADR）并实施，不写过渡性 `RFC`**：
   - 方案推演在对话/Plan 模式中完成；一旦明确，直接将选型理由与淘汰方案写入 `ARCHITECTURE.md`（或 `docs/adr/`）并立即改代码。未想清楚的方案不落盘。
3. **显式空间坐标系优先与单一视觉/数据契约真源（Production-as-Truth & Schema-as-Contract）**：
   - **显式数学坐标优于隐式盒模型盲猜（以高密度空间/图表 UI 为例）**：
     - 大模型没有视觉直觉，写复杂嵌套 CSS 极易出现重叠、错位或退化成千篇一律的后台方框；而在需要精准空间表达的场景（如价格色带、筹码分布、多锚点防重叠刻度尺或架构拓扑图），采用显式二维笛卡尔坐标系（如声明式内联 `<svg viewBox>` 配合编译期响应式绑定）能让 AI 直接通过解析几何计算精准定位。
     - 当高保真原型或设计已采用显式 `<svg>` 坐标系建立空间视觉表达时，Worker 在实现生产前端时必须完整保留该坐标系，严禁偷懒将其拆碎退化为孤立的 HTML `div` 文本条。
   - **单一视觉与数据契约真源（Production-as-Truth）**：建仓初期的静态原型一旦合入生产组件库，立即以**生产组件与样式系统**为唯一视觉真源（及时退役早期静态草稿，防止后续波次 Worker 被过时原型带偏），且不再维护重复的文字版 `DESIGN.md`；前后端数据结构由单一代码真源（如 `schema` → OpenAPI → 强类型客户端）自动导出生成，不手写易过期的接口协议文档。

## Mono-repo 的继承与自治

Mono-repo 的核心是**防止规则重复与跨模块越权**：

- **仓库层（根 `AGENTS.md` 与 `docs/ARCHITECTURE.md`）**：负责子项目集合、允许的依赖方向、跨模块验证命令和共同部署约束。
- **模块层（子目录 `AGENTS.md`）**：默认继承根入口约束。只有当某模块有独立的公共 API、特殊红线或独立交接节奏时，才建立模块的 `AGENTS.md`，且不重复抄写根级规则。
- **不假设自动加载**：不同 Agent 宿主对子目录指令的自动加载行为不同。根 `AGENTS.md` 必须提供清晰的模块路由表，引导跨模块任务显式读取所有受影响模块的契约。

## 规则演化的三阶漏斗（`LESSONS.md` → 正式规则）

踩坑经验不能永远堆积在 `LESSONS.md` 里变成没人读的长文，也不能一拍脑袋就写进全局死规矩：

```text
真实失败事件
  ↓ 记录证据、根因与候选规则
docs/LESSONS.md（待验证缓冲池）
  ↓ 同一模式重复出现 3 次，或单次造成严重事故
按所有者晋升并删除 LESSONS 正文（只留指向正式规则的链接）：
  ├── 可机械校验的实现约束   → Router 直接安排 Worker 固化为 Linter/测试守卫
  ├── 属于本项目全局边界     → 标 blocked 交 Brain 与人审议后写入根 AGENTS.md 或 ARCHITECTURE.md
  └── 属于跨项目通用工作方法 → 标 blocked 交 Brain 与人审议后晋升至对应 Skill（如 engineering-discipline）
```

**最高级的规则晋升是变成自动化检查（Linter / Test / CI 门禁）**；能用确定性脚本拦住的错误，不靠文档叮嘱。
