# 多 Agent 双环协作 Skill

## 为什么拆角色

角色拆分只看两种差异，不看能力差异：

- **信息差异**：作者的上下文里装着“我为什么这么写”，自己验收会退化为自我确认，所以 Worker 与 Tester 必须分开。
- **交互对象差异**：面对人类聊天的会话与由自动化唤醒的后台会话，阻塞语义完全不同。后台总控若不知道自己是无人值守的 Router，收到唤醒消息就会以为对面有人，遇到一点授权疑问就停下来提问，闭环卡死在没人看的窗口里。

因此采用双环：人只面对思考环里的 Brain；执行环由 Router 调度 Worker 与 Tester，另有按需派生的 Auditor。设计推导见 [references/rationale.md](references/rationale.md)。

## 角色

| 角色 | 所在环与交互对象 | 职责 | 模型倾向 | 不做什么 |
| --- | --- | --- | --- | --- |
| **Brain** | 思考环，唯一面对人类 | 承接人类意图，做产品与架构决策、冻结上游公共契约；向 `docs/TASKS.md` 追加或改写任务区块并只提交该文件；处理 `blocked` 与最终审美裁定 | 旗舰模型 | 不写业务代码；不覆盖或删除仍为 `pending` 的任务；不把冗长工具日志带进对话 |
| **Router** | 执行环，常驻；由自动化唤醒，对面没有人 | 取单、调度 Worker 与 Tester、管理任务 Worktree；Tester 打回时现场分诊、记 `docs/LESSONS.md` 并直接拍板返工；结案、排空队列、睡前派生 Auditor | 次旗舰，决断力强 | **不停下向人类提问、不等待回复、不短超时早退**；不把显性问题转给 Brain；取单不改状态、不提交；不写业务代码 |
| **Worker** | 执行环，面对 Router | 开工前读 `docs/LESSONS.md`；在主工作树或分配的 Worktree 内实现完整垂直切面，交卷前跑通工程门禁并做 UI 自检 | 次旗舰，编码执行力强 | 不直接面对人类；不改上游冻结契约；不写内部 Mock 或脱离真实环境的假测试；不给自己下验收结论 |
| **Tester** | 执行环，面对 Router | 按产品形态模拟真实用户验收，首轮穷尽缺陷，归档证据，核对授权边界，向 Router 出报告 | 次旗舰，工具与视觉能力强 | 不替 Worker 写代码或测试；不拿脚本绿灯当体验验收；不做快照备份、进程扫描等防御性内耗；不碰用户真实数据 |
| **Auditor** | 执行环内由 Router 按需派生的一次性全新会话，不由钩子或外部进程拉起 | 队列排空后审查一段提交区间，只报告有实证的问题 | 旗舰，审美与代码洁癖强 | 不复用任何旧会话上下文；不提没有实证的主观风格建议 |

无需跨会话或跨宿主的简单项目里，Brain 与 Router 可由同一个主会话兼任；一旦拆成跨窗口或跨宿主的双环，必须显式立住 Router 身份。

## 任务状态与调度板

`docs/TASKS.md` 是两环之间唯一的交接面。每个任务是一个独立区块 `## [Task #N] <标题>`，带 `Status` 与写作用域 `Scope`（格式见下文“通信契约”）。

- **状态值**：`pending | verified | blocked | superseded`。`pending` 同时表示排队中和执行中，没有“进行中”状态。
- **Brain 只追加或标废**：新任务追加在末尾，不覆盖或删除仍为 `pending` 的区块；推翻一个未完成的任务时，把它改为 `superseded (by #M)` 并追加新任务。Brain 每次只提交 `docs/TASKS.md`（`git commit --only docs/TASKS.md`），不把后台 Worker 尚未提交的代码带进提交。
- **滑动窗口**：文件里只保留未结案区块（`pending`、`blocked`）和最近 1~2 个已结案区块（`verified`、`superseded`）作锚点，更早的在追加新单时移出，历史交给 `git log`。
- **两级分诊**：面对大量外部 Issue 或 PR 时，先在仓外去重、聚类、筛掉噪音，只把近期确认要做的任务放上调度板。

## Router 执行循环

Router 由自动化唤醒，是任务队列唯一的消费者：

1. **取单**：按序取一项 `pending` 任务。取单时不改状态、不提交。
2. **实现**：派 Worker 实现并提交业务代码，Worker 交卷前必须跑通工程门禁（见下文“验证分工”）。
3. **验收**：派 Tester 对该业务提交做真实用户验收。
4. **打回时现场处理（显性问题不出执行环）**：
   - 实现漏项、交互或排版瑕疵、测试逃逸，以及完成任务目标所需、但任务包漏列的同切面支撑文件（只要不在“不在范围内”或禁区里），一律由 Router 当场拍板：直接授权补改、指明根因方向，让 Worker 返工、Tester 复验，不转给 Brain；
   - 每次打回，Router 对比 Worker 自检报告与 Tester 的发现，把“为什么没在自检中被拦下”记入 `docs/LESSONS.md`（新增或累加 `Seen N×`）；
   - 某条规则累计 `Seen 3×` 或属严重回归：能写成测试的，令 Worker 在返工时固化为 `tests/` 下的守卫测试；需要改项目契约文档或 Skill 才能落实的，标 `blocked` 交 Brain 与人裁定。晋升后把该条从 `docs/LESSONS.md` 正文移到文末的已晋升列表，只留指向守卫测试或正式文档的记录；
   - Worker 连续两轮在同一症状上打表层补丁时，Router 介入止损，重新判定根因与修法。
5. **升级（`blocked`）**：只在以下情况把证据写回该任务区块、状态改为 `blocked`，并只提交 `docs/TASKS.md`：需要改动上游已冻结的公共契约或契约本身自相矛盾；需要触碰任务包“不在范围内”或禁区里的文件；需求有业务价值上的二义性需要人取舍；涉及破坏性操作；同一任务连续 3 轮返工仍未通过验收。
6. **结案**：先重读 `docs/TASKS.md`，确认该任务没有被 Brain 标为 `superseded`；再只改该区块的状态行为 `verified`，在 `Verified-Commit` 填通过验收的业务提交 SHA，然后只提交 `docs/TASKS.md`。
7. **排空**：每次提交后、结束回合前重读 `docs/TASKS.md`。只要还有 `pending` 任务（包括执行期间 Brain 新追加、但没有单独唤醒你的任务），就在当前回合继续执行，不等新的唤醒。
8. **睡前审计**：队列排空后，若 `docs/LESSONS.md` 首行 `reviewed-through` 之后已有不少于 5 个非 `docs/` 代码提交，派生一个全新的、不复用旧上下文的 Auditor 审查该区间。Auditor 只报告三类实证：
   - **改坏不红**：注释或改反被测核心代码后，测试仍然通过；
   - **反模式行号**：指出 `文件:行号` 处违反明文禁止的写法（同名包装、事件截胡、用固定延时等待就绪、读源码字符串做假测试等）；
   - **契约背叛**：指出代码或任务单违背 `ARCHITECTURE.md`、`PRODUCT.md` 的具体条目。

   有实证时，当场让 Worker 清理、Tester 复验；全部干净后把 `docs/LESSONS.md` 首行的 `reviewed-through` 更新为最新 `HEAD` 并提交（这次提交只含 `docs/LESSONS.md`），然后休眠。

“只提交 `docs/TASKS.md`”约束的是派单、升级与结案这类调度提交；`docs/LESSONS.md` 的记账与水位线提交单独进行，同样不夹带业务代码。

## 验证分工

- **Worker 交卷前置条件**：编译、类型与静态检查、全仓单元测试与守卫测试、构建打包全部跑通（不只跑改动所在的包）；对新增或修改的关键测试做手动破坏验证（故意改坏被测逻辑，确认测试变红，再改回）；业务提交的正文写明意图或根因与验证证据；涉及 UI 的改动，自己对真实渲染结果截 1~3 张图存入 `.tmp/evidence/task-<ID>/`，并用图像查看工具亲自看一遍，当场修掉明显的重叠、截断、错位。
- **Tester 只做一件事：模拟真实用户**。怎么验由产品形态决定：CLI 按用户手册敲命令看输出，API 发真实请求看状态流转，GUI 与网页在专用沙盒里像普通用户一样操作并逐屏截图检查排版、位置与文案。第一轮验收就把该任务切面的问题一次列全，不分轮挤牙膏；通过验收的截图保留在 `.tmp/evidence/task-<ID>/` 供人做最终审美裁定。

## 并发与 Worktree

| 任务类型 | 并发上限 | 前提 |
| --- | --- | --- |
| 局部微调或上游契约冻结 | 0（Brain 直接做） | 不超过 5 步工具调用；涉及完整业务切面或耗时测试的，交给执行环 |
| 共享工作树写入 | 1 | 队列只有一项且主工作树空闲时直接在主工作树执行；同一工作树同一时刻只有 1 个写代码的 Worker |
| Worktree 并行写 | 2~3 | Tester 正在主工作树验收上一单（流水线重叠），或多项任务的 `Scope` 完全不重叠且上游共享 Schema 已冻结 |
| 只读探索、分诊、审查 | 2~4 | 按正交子系统或审查维度扇出，不按零碎文件拆分 |

Worktree 由 Router 独占管理，具体 git 操作由 Router 自行处理，协议只约束三点：

1. **何时开**：只在上表的流水线重叠或正交并行写场景开启，其余情况在主工作树执行。
2. **开在哪**：统一建在本仓库内被忽略的 `.tmp/worktrees/task-<ID>`，不用全局共享临时目录或仓库外的父目录。放在未被忽略的目录时，主工作树的一次 `git add -A` 会把它当作嵌套仓库暂存进提交。
3. **用完清理**：任务合入 `main` 或被标为 `superseded` 后，删除对应 Worktree 与任务分支，`.tmp/worktrees/` 里只保留正在开发的目录。

## 上下文管理

- **Inline & Spill**：Brain 与 Router 只在对话里保留任务 ID、结论摘要和文件路径，完整细节与证据写到工作区文件里按需读取。
- **复用热会话**：Router 在项目周期内复用已驻留的 Worker 与 Tester 会话，以利用提示缓存、避免每次冷启动重读。

## 通信契约

角色之间通过下面两种结构化文本交接，不靠口头的模糊指令。

### 任务区块（Brain 写入 `docs/TASKS.md`）

```markdown
## [Task #<N>] <任务名称>
- **Status**: pending
- **Scope**: `<允许修改的文件或目录前缀，供 Router 判断能否并行>`
- **Verified-Commit**: none
- **Updated**: <YYYY-MM-DD>
- **授权范围**：允许修改的文件与目录、只读依赖的模块（完成本任务所需的同切面支撑文件，Router 可直接授权补改）
- **不在范围内**：明确排除的功能，以及不可触碰的目录（上游冻结契约、用户真实数据等）
- **接口与行为契约**：输入、输出、边界条件、错误处理、性能要求
- **Worker 工程门禁**：交卷前必须跑通的全仓测试、守卫测试、破坏验证与构建命令
- **Tester 验收要求**：按产品形态的真实用户操作路径、要检查的视觉与交互点、期望结果
```

### 验收报告（Tester → Router）

```markdown
# 验收报告：[Task #<N>] <任务名称>
- **结论**：通过 | 实现或体验问题（退回 Worker） | 核心契约冲突（由 Router 标记 blocked）
- **边界核对**：是否触碰未授权的契约；Worker 的全仓门禁与破坏验证是否齐备
- **真实用户验收证据**：实际操作过程、截图检查结论或真实输出记录
- **必须修复项**：现象、违背的用户预期或契约条目、复现路径、对应文件位置
- **需升级裁定项**：契约冲突点或架构缺陷说明
```

## 唤醒机制

默认参考实现是 Git 总线：Brain 提交 `docs/TASKS.md` 新增的 `pending` 任务，`post-commit` 钩子按 diff 边沿触发唤醒该项目专属的常驻 Router；Router 自己的结案提交不新增 `pending` 行，不会自激。钩子模板、唤醒消息与审计计数命令见 [references/git-bus.md](references/git-bus.md)。

## 升级链与人的介入

升级链固定为：`Worker ↔ Tester ↔ Router → Brain → 人`。

- **不出执行环**：显性实现或体验缺陷、任务包漏列的同切面支撑文件，由 Router 现场裁决（见执行循环第 4 步）。
- **Router 退回 Brain**：执行循环第 5 步列出的情况。
- **Brain 唤醒人**：需要改变项目对外目标或范围；多个技术方案之间存在业务价值取舍；收到 `blocked` 需要人做方向裁定。

## 验收清单

- [ ] 角色边界清晰：Brain 面向人类定契约，Router 管执行环、现场分诊并记 `docs/LESSONS.md`，Worker 实现并跑通全仓门禁与破坏验证，Tester 独立模拟真实用户验收
- [ ] `docs/TASKS.md` 采用独立任务区块与 `Scope`；Brain 与 Router 都只提交该文件；Router 精确结案并在睡前排空全部 `pending`
- [ ] Router 收到唤醒后没有停下向人类提问，也没有短超时早退
- [ ] 同一工作树没有多个 Agent 同时写；并行开发都在 `.tmp/worktrees/` 下的独立 Worktree 中，合入后已清理
- [ ] Tester 的放行依据是符合产品形态的真实用户操作与观测证据，而不是重跑测试脚本
- [ ] 角色定义不依赖特定宿主、模型型号或调试框架
