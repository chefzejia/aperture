# 多 Agent 双环协作 Skill

## 为什么拆角色

角色拆分只看两种差异，不看能力差异：

- **信息差异**：作者的上下文里装着“我为什么这么写”，自己验收会退化为自我确认，所以 Worker 与 Tester 必须分开。
- **交互对象差异**：面对人类聊天的会话与由自动化唤醒的后台会话，阻塞语义完全不同。后台总控若不知道自己是无人值守的 Router，收到唤醒消息就会以为对面有人，遇到一点授权疑问就停下来提问，闭环卡死在没人看的窗口里。

因此采用双环：人只面对思考环里的 Brain；执行环由 Router 派生并调度 Worker 与 Tester，另有按需派生的 Auditor。设计推导见 [references/rationale.md](references/rationale.md)。

## 角色

| 角色 | 所在环与交互对象 | 职责 | 模型倾向 | 不做什么 |
| --- | --- | --- | --- | --- |
| **Brain** | 思考环，唯一面对人类 | 承接人类意图，做产品与架构决策、冻结上游公共契约；向 `docs/TASKS.md` 追加或标废**里程碑**区块并只提交该文件；处理 `blocked` 与最终审美裁定 | 旗舰模型 | 不写业务代码；不覆盖或删除仍为 `pending` 的里程碑，要改就标 `superseded` 再追加新的；不把冗长工具日志带进对话 |
| **Router** | 执行环，唯一常驻会话；由自动化唤醒，对面没有人 | 取单、**派生**切片 Worker 与里程碑 Tester、管理 Worktree；Tester 打回时现场分诊、记 `docs/LESSONS.md` 并直接拍板返工；结案、排空队列、按条件派生 Auditor | 次旗舰，决断力强 | **不停下向人类提问、不等待回复、不短超时早退**；不把显性问题转给 Brain；取单不改状态、不提交；**不自己改切片代码，哪怕只有两行**，只派生不代做 |
| **Worker** | 执行环，面对 Router；从切片派出到所在里程碑结案，期间保留供返工，结案后关闭 | 开工前读 `docs/LESSONS.md`；在主工作树或分配的 Worktree 内实现一个完整切片，交卷前跑通工程门禁并做 UI 自检 | 次旗舰，编码执行力强 | 不直接面对人类；不改上游冻结契约；不写内部 Mock 或脱离真实环境的假测试；不给自己下验收结论 |
| **Tester** | 执行环，面对 Router；每个里程碑派生一个全新会话，同一里程碑内的返工复验沿用，结案后关闭 | 按产品形态模拟真实用户验收整个里程碑，一轮穷尽缺陷，归档证据，核对授权边界，向 Router 出报告 | 次旗舰，工具与视觉能力强 | 不替 Worker 写代码或测试；不拿脚本绿灯当体验验收；不做快照备份、进程扫描等防御性内耗；不碰用户真实数据 |
| **Auditor** | 执行环内由 Router 按需派生的一次性全新会话，不由钩子或外部进程拉起 | 队列排空且满足审计条件时，审查 `reviewed-through` 之后的提交区间，只报告有实证的问题 | 旗舰，审美与代码洁癖强 | 不复用任何旧会话上下文；不提没有实证的主观风格建议 |

无需跨会话或跨宿主的简单项目里，Brain 与 Router 可由同一个主会话兼任；一旦拆成跨窗口或跨宿主的双环，必须显式立住 Router 身份。

## 会话生命周期

状态在文件和 Git 里，不在会话里。Router 是唯一常驻的会话：它是队列的唯一消费者，正在运行时新的唤醒排队，不会出现两个 Router 并发排空同一个队列。Worker、Tester、Auditor 都按需派生、用完即关。

- **Worker**：从切片派出到所在里程碑结案，期间保留供返工。新 Worker 接不住上一个里程碑的工作，说明控制面（代码、commit body、`ARCHITECTURE.md`、`LESSONS.md`）有缺口，补缺口，不靠留着会话。
- **Tester**：每个里程碑派生一个全新会话，保持“不懂实现的新用户”视角；同一里程碑内的返工复验沿用，它知道自己列过哪些问题。
- **提示缓存**：宿主若能命中是红利，协议不依赖它。

## 里程碑与调度板

`docs/TASKS.md` 是两环之间唯一的交接面。调度单位是**里程碑**：一条真实用户路径能端到端走通、Tester 一轮就能判定的可观测增量。每个里程碑是一个独立区块 `## [Milestone #N] <标题>`，内含若干**切片**（格式见下文“通信契约”）。

- **状态值**：`pending | verified | blocked | superseded`，只存在于里程碑上，切片没有独立状态。`pending` 同时表示排队中和执行中，没有“进行中”状态。
- **切片**：Worker 的工作单位，各带写作用域 `Scope`。Scope 重叠或有串行依赖的并成同一个切片；Scope 正交才分开。只有一个切片的里程碑直接在区块里写 `Scope`，不单列切片。一个里程碑暂定 3~5 个切片封顶，按打回率调整。
- **里程碑的切点**：用户路径闭合；后续工作建立在尚未验证的体验决策上；不可逆或高风险操作之前。
- **前置（`Depends-On`）**：里程碑之间的先后写在 `Depends-On` 字段里，不另设排队状态。前置全部 `verified` 后才可派发；前置被标 `superseded (by #M)` 时改看 #M；前置被标 `blocked` 时，依赖它的里程碑保持 `pending`、不派发，等 Brain 处理。
- **Brain 只追加或标废**：新里程碑追加在末尾，不覆盖或删除仍为 `pending` 的区块；要改一个未完成的里程碑，一律把它改为 `superseded (by #M)` 并追加新里程碑，不做原地局部改写。Brain 每次只提交 `docs/TASKS.md`（`git commit --only docs/TASKS.md`），不把后台 Worker 尚未提交的代码带进提交。
- **已提交的切片代码默认不回滚**：新里程碑在当前 HEAD 上继续，要回滚由新里程碑明写。
- **滑动窗口**：文件里只保留未结案区块（`pending`、`blocked`）和最近 1~2 个已结案区块（`verified`、`superseded`）作锚点，更早的在追加新单时移出，历史交给 `git log`。
- **两级分诊**：面对大量外部 Issue 或 PR 时，先在仓外去重、聚类、筛掉噪音，只把近期确认要做的事组织成里程碑放上调度板。

## Router 执行循环

Router 由自动化唤醒，是里程碑队列唯一的消费者，只派生、不改切片代码：

1. **取单**：每次取单前重读项目的角色契约（`docs/ROLES.md`）与 `docs/TASKS.md`，协议改动因此在下一个里程碑生效，不依赖重新唤醒。按序取第一个前置已满足的 `pending` 里程碑。取单时不改状态、不提交。
2. **派切片**：每次派发前重读 `docs/TASKS.md`；若该里程碑已被标为 `superseded`，立即停止派发，清理对应 Worktree 与分支，转去下一个 `pending`。Scope 正交的切片可并行（见下文“并发与 Worktree”），有依赖的按序派。
3. **切片实现**：派 Worker 实现并提交业务代码，Worker 交卷前必须跑通工程门禁（见下文“验证分工”）。
4. **验收**：所有切片提交、门禁证据齐备后，里程碑改变了外部可观测表面（GUI、CLI、API 行为）就派一个全新的 Tester 一轮验收；验收栏写“无”（内部重构、测试、文档、工具）则跳过 Tester，靠 Worker 的 commit body 门禁证据与 Auditor 兜底。
5. **打回时现场处理（显性问题不出执行环）**：
   - 实现漏项、交互或排版瑕疵、测试逃逸，以及完成里程碑目标所需、但切片漏列的同切面支撑文件（只要不在“不在范围内”或禁区里），一律由 Router 当场拍板：直接授权补改、指明根因方向，按报告里的文件位置归因到切片，让对应 Worker 返工、同一 Tester 复验，不转给 Brain；
   - 每次打回，Router 对比 Worker 自检报告与 Tester 的发现，把“为什么没在自检中被拦下”记入 `docs/LESSONS.md`（新增或累加 `Seen N×`），`Seen N×` 按缺陷模式计，不按打回次数计；
   - 某条规则累计 `Seen 3×` 或属严重回归：能写成测试的，令 Worker 在返工时固化为 `tests/` 下的守卫测试；需要改项目契约文档或 Skill 才能落实的，标 `blocked` 交 Brain 与人裁定。晋升后把该条从 `docs/LESSONS.md` 正文移到文末的已晋升列表，只留指向守卫测试或正式文档的记录；
   - Worker 连续两轮在同一症状上打表层补丁时，Router 介入止损，重新判定根因与修法。
6. **升级（`blocked`）**：只在以下情况把证据写回该里程碑区块、状态改为 `blocked`，并只提交 `docs/TASKS.md`：需要改动上游已冻结的公共契约或契约本身自相矛盾；需要触碰里程碑“不在范围内”或禁区里的文件；需求有业务价值上的二义性需要人取舍；涉及破坏性操作；同一里程碑连续 3 轮返工仍未通过验收。
7. **结案**：先重读 `docs/TASKS.md`，确认该里程碑没有被 Brain 标为 `superseded`；再只改该区块的状态行为 `verified`，在 `Verified-Commit` 填通过验收时的业务提交 SHA，然后只提交 `docs/TASKS.md`（项目有功能台账时，按下文“功能台账”一节同步所列的行，一并提交 `docs/FEATURES.md`）；最后关闭该里程碑的 Worker 与 Tester，删除对应 Worktree。
8. **排空**：每次提交后、结束回合前重读 `docs/TASKS.md`。只要还有前置已满足的 `pending` 里程碑（包括执行期间 Brain 新追加、但没有单独唤醒你的里程碑），就在当前回合继续执行，不等新的唤醒；只剩前置未满足的 `pending` 时即可休眠。
9. **睡前审计**：队列排空后，满足任一条件即派生一个全新的、不复用旧上下文的 Auditor，审查 `docs/LESSONS.md` 首行 `reviewed-through` 之后的区间：自上次审计起已结案不少于 2 个里程碑（初始值，项目可在 `docs/ROLES.md` 里按审出的实证数调整），或其间有里程碑跳过了 Tester。Auditor 只报告三类实证：
   - **改坏不红**：注释或改反被测核心代码后，测试仍然通过；
   - **反模式行号**：指出 `文件:行号` 处违反明文禁止的写法（同名包装、事件截胡、用固定延时等待就绪、读源码字符串做假测试等）；
   - **契约背叛**：指出代码或里程碑区块违背 `ARCHITECTURE.md`、`PRODUCT.md` 的具体条目。

   有实证时，当场派生新的 Worker 清理，再按上文第 4 步的规则决定是否派 Tester 复验；全部干净后把 `docs/LESSONS.md` 首行的 `reviewed-through` 更新为最新 `HEAD` 并提交（这次提交只含 `docs/LESSONS.md`），然后休眠。

“只提交 `docs/TASKS.md`”约束的是派单、升级与结案这类调度提交；`docs/LESSONS.md` 的记账与水位线提交单独进行，同样不夹带业务代码。结案时同步的 `docs/FEATURES.md` 是例外，它记的正是这次结案的结论。

## 验证分工

- **Worker 每个切片的交卷前置条件**：编译、类型与静态检查、全仓单元测试与守卫测试、构建打包全部跑通（不只跑改动所在的包）；对新增或修改的关键测试做手动破坏验证（故意改坏被测逻辑，确认测试变红，再改回）；业务提交的正文写明意图或根因与验证证据；涉及 UI 的改动，自己对真实渲染结果截 1~3 张图存入 `.tmp/evidence/milestone-<N>/`，并用图像查看工具亲自看一遍，当场修掉明显的重叠、截断、错位。门禁与验收的默认值写在项目的 `docs/ROLES.md`，里程碑里只写偏离默认的项。
- **Tester 只做一件事：模拟真实用户**。怎么验由产品形态决定：CLI 按用户手册敲命令看输出，API 发真实请求看状态流转，GUI 与网页在专用沙盒里像普通用户一样操作并逐屏截图检查排版、位置与文案。每个里程碑一轮验收，把整条用户路径上的问题一次列全，不分轮挤牙膏；通过验收的截图保留在 `.tmp/evidence/milestone-<N>/`，这就是人做最终审美裁定的节点。

## 功能台账（可选）

项目建了 `docs/FEATURES.md`（何时建立与格式见 `project-governance` Skill）时，里程碑与台账按下面四条联动。跳过 Tester 的里程碑靠它记下验收债，不让旧验收悄悄过期。

1. **列条目**：Brain 在里程碑的 `Features` 字段列出它推进或动到的条目，没有写“—”；条目增删归 Brain。
2. **逐行结论**：Tester 的验收报告按这些条目逐行写结论与未覆盖的部分。
3. **结案同步**：Router 在结案提交里同步所列的行，只改这些行。独立验收通过的改为 `已验收`，写 `#<里程碑> @<Verified-Commit>（日期）`；动到但没有独立验收的降为 `待复验`，验收栏写“无”、跳过 Tester 的里程碑也照此处理。这次提交同时包含 `docs/TASKS.md` 与 `docs/FEATURES.md`（`git commit --only docs/TASKS.md docs/FEATURES.md`）。
4. **发布前清债**：写明发布版本的里程碑，先把这个版本范围内的 `待复验` 条目按真实用户路径重新独立验收，再发布；自动化测试是绿的不能代替这一步。

## 并发与 Worktree

| 工作类型 | 并发上限 | 前提 |
| --- | --- | --- |
| 局部微调或上游契约冻结 | 0（Brain 直接做） | 不超过 5 步工具调用；涉及完整业务切面或耗时测试的，交给执行环 |
| 共享工作树写入 | 1 | 里程碑只有一个切片且主工作树空闲时直接在主工作树执行；同一工作树同一时刻只有 1 个写代码的 Worker |
| Worktree 并行写 | 2~3 | 同一里程碑内 `Scope` 正交的切片且上游共享 Schema 已冻结；或下一个里程碑与当前里程碑的 `Scope` 完全正交（流水线重叠，默认关闭，因为会建立在尚未验收的代码之上） |
| 只读探索、分诊、审查 | 2~4 | 按正交子系统或审查维度扇出，不按零碎文件拆分 |

Worktree 由 Router 独占管理，具体 git 操作由 Router 自行处理，协议只约束三点：

1. **何时开**：只在上表的正交并行写场景开启，其余情况在主工作树执行。
2. **开在哪**：统一建在本仓库内被忽略的 `.tmp/worktrees/m<N>-s<K>`，不用全局共享临时目录或仓库外的父目录。放在未被忽略的目录时，主工作树的一次 `git add -A` 会把它当作嵌套仓库暂存进提交。
3. **用完清理**：切片合入 `main` 或所在里程碑被标为 `superseded` 后，删除对应 Worktree 与分支，`.tmp/worktrees/` 里只保留正在开发的目录。

## 上下文管理

- **Inline & Spill**：Brain 与 Router 只在对话里保留里程碑 ID、结论摘要和文件路径，完整细节与证据写到工作区文件里按需读取。

## 通信契约

角色之间通过下面两种结构化文本交接，不靠口头的模糊指令。

### 里程碑区块（Brain 写入 `docs/TASKS.md`）

```markdown
## [Milestone #<N>] <用户能做到什么>
- **Status**: pending
- **Verified-Commit**: none
- **Depends-On**: —（有前置时写编号，如 `#12, #13`）
- **Features**: —（项目有功能台账时，列出推进或动到的条目 ID）
- **用户可观测目标**：这个里程碑完成后，用户能端到端做到什么
- **Tester 验收**：一条真实用户操作路径、要检查的视觉与交互点、期望结果，一轮跑完；没有外部可观测变化时写“无”
- **不在范围内**：明确排除的功能，以及不可触碰的目录（上游冻结契约、用户真实数据等）

### 切片
1. **S1** `Scope: <允许修改的文件或目录前缀>`：行为契约（输入、输出、边界条件、错误处理、性能要求）；完成本切片所需的同切面支撑文件，Router 可直接授权补改
2. **S2** `Scope: <前缀>`：行为契约；Scope 与 S1 正交才单独成片
3. **S3**（依赖 S1）`Scope: <前缀>`：行为契约；有串行依赖或 Scope 重叠的并入同一切片
```

工程门禁与验收方式的默认值写在项目的 `docs/ROLES.md`，区块里只写偏离默认的项，更新时间由 Git 记录。只有一个切片时，`Scope` 直接写在区块里，省掉切片小节。

### 验收报告（Tester → Router）

```markdown
# 验收报告：[Milestone #<N>] <里程碑名称>
- **结论**：通过 | 实现或体验问题（退回 Worker） | 核心契约冲突（由 Router 标记 blocked）
- **边界核对**：是否触碰未授权的契约；Worker 的全仓门禁与破坏验证是否齐备
- **真实用户验收证据**：实际操作过程、截图检查结论或真实输出记录
- **台账逐行结论**：里程碑列了 `Features` 时，按条目写通过、未通过与未覆盖的部分
- **必须修复项**：现象、违背的用户预期或契约条目、复现路径、对应文件位置
- **需升级裁定项**：契约冲突点或架构缺陷说明
```

## 唤醒机制

默认参考实现是 Git 总线：Brain 提交 `docs/TASKS.md` 新增的 `pending` 里程碑，`post-commit` 钩子按 diff 边沿触发唤醒该项目专属的常驻 Router；Router 自己的结案提交不新增 `pending` 行，不会自激。钩子模板、唤醒消息与审计计数命令见 [references/git-bus.md](references/git-bus.md)。

## 升级链与人的介入

升级链固定为：`Worker ↔ Tester ↔ Router → Brain → 人`。

- **不出执行环**：显性实现或体验缺陷、切片漏列的同切面支撑文件，由 Router 现场裁决（见执行循环第 5 步）。
- **Router 退回 Brain**：执行循环第 6 步列出的情况。
- **Brain 唤醒人**：需要改变项目对外目标或范围；多个技术方案之间存在业务价值取舍；收到 `blocked` 需要人做方向裁定。

## 验收清单

- [ ] 角色边界清晰：Brain 面向人类定契约，Router 只派生不代做、现场分诊并记 `docs/LESSONS.md`，Worker 实现切片并跑通全仓门禁与破坏验证，Tester 按里程碑独立模拟真实用户验收
- [ ] `docs/TASKS.md` 采用独立里程碑区块与切片 `Scope`；Brain 与 Router 都只提交该文件；Router 每次派切片前重读该文件，精确结案并在睡前排空全部 `pending`
- [ ] 只有 Router 常驻；Worker 与 Tester 在里程碑结案后已关闭，Tester 每个里程碑都是全新会话
- [ ] 里程碑之间的先后只写在 `Depends-On` 里，没有另设排队状态；Router 每次取单前重读 `docs/ROLES.md`
- [ ] 有功能台账时，结案提交同步了里程碑所列的行，跳过 Tester 而动到的条目已降为 `待复验`
- [ ] Router 收到唤醒后没有停下向人类提问，也没有短超时早退
- [ ] 同一工作树没有多个 Agent 同时写；并行开发都在 `.tmp/worktrees/` 下的独立 Worktree 中，合入后已清理
- [ ] Tester 的放行依据是符合产品形态的真实用户操作与观测证据，而不是重跑测试脚本
- [ ] 角色定义不依赖特定宿主、模型型号或调试框架
