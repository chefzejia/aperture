# 双环协作角色设计原理

## 第一性原理：什么时候才应该拆分角色？

**角色边界成立的唯一依据：合并它会产生一个可以说出名字的具体失败。**

在多 Agent 系统中，每增加一个角色就会增加一次“上下文转述损耗”和“协调开销”。
- **能力差异不是拆分理由**：同一个高水平模型既能做架构设计，也能写业务代码，还能做代码审查。
- **信息差异（Context Asymmetry）与交互对象差异（Human-Facing vs Unattended Automation）才是拆分理由**：当某一段上下文的存在本身会干扰另一项判断，或者一个会话是面向真人实时聊天、另一个会话是后台无人值守自动机时，才必须进行角色与会话隔离。

## 为什么完整形态是现在的角色划分？（从 Brain · Worker · Tester 到加入 Router 与 Auditor 的实测演进）

### 1. 为什么在宏观层 `Brain = Architect`（必须合并）
- **上下文同构**：宏观协调者与架构师需要完全相同的上下文——项目目标、产品审美、模块边界与关键技术决策。
- **唯一人类入口**：人只盯这 1 个窗口，和旗舰模型做高密度的思想碰撞，定稿后写入 `docs/TASKS.md (Status: pending)` 并执行 `git commit --only docs/TASKS.md`。

### 2. 为什么在执行环必须独立出 `Router（无人值守执行总控）`，而不能只写 Brain / Worker / Tester？
- **具体失败名称：“后台会话身份迷失（停下来向空气提问）”**。
- **真实翻车机制**：
  - 当我们用 `.git/hooks/post-commit` 通过队列把自然语言消息（如 `"请读取并执行"`）塞进后台常驻的总控会话时，如果 `docs/ROLES.md` 里只写了 `Brain / Worker / Tester`；
  - 一旦独立 Tester 在验收时发现完成本任务目标必须连带修改某个同切面支撑文件（而切片的授权范围漏列了该文件），Worker 不敢越权修改并上报给后台总控；
  - 此时后台总控看到自己身处一个聊天窗口、且刚收到一条 `user message`，就会误以为对面坐着人类用户，直接在后台窗口里停下来礼貌提问“请问允许我扩大修改范围吗？”，导致无人值守闭环当场卡死在没人看的后台窗口里。
- **立住 `Router`（执行环的战术总控与现场法官）的工程收益**：
  - 在 `ROLES.md` 与唤醒消息（`[AUTO-WAKEUP] 你是本项目的无人值守 Router...`）中明确宣告它的无人值守身份：它由自动化唤醒，对面没有人在看，不能停下提问等待回复，也不能把显性 Bug 转给 Brain；
  - 赋予 Router 明确的**战术自愈闭环权与 `LESSONS.md` 执笔权（显性问题不出执行环，战略冲突才报 Brain）**：
    1. **显性问题现场拍板**：当 Tester 发现实现/体验缺陷或完成本任务目标必需的同切面支撑文件漏列（未触碰禁区黑名单）时，Router 直接扩权支撑文件、指出根因方向（同一机制在同一里程碑内二次出现或已晋升守卫复发时，停止表层补丁改派机制级修复与输入维度矩阵测试，见下文「缺陷归类」），直接调度 Worker 修复并重跑 Tester；
    2. **执笔 `docs/LESSONS.md` 与 `Seen 3×` 守卫自进化**：Worker 视野局限在局部实现，Tester 视角是纯粹的不懂代码用户，**唯有 Router 同时握有“Worker 自检报告”与“Tester 翻车现场”**。因此每当发生 Tester 打回（说明残次品逃过了 Worker 的自检门禁），由 Router 亲自比对两边信息，将漏检模式写入或累加至 `docs/LESSONS.md (Seen N×)`；一旦某条显性工程规则达 `Seen 3×`，Router 当场指令 Worker 在返工时顺手将其写成 `tests/` 下的静态守卫单测（Guard Test），无需人类熬夜手动巡检即可完成防线自进化；
    3. **战略冲突升级**：仅当真正触及上游已冻结的公共契约自相矛盾、需求存在业务价值二义性需人类取舍、或连续 3 轮战术修复仍失败时，Router 才将完整证据写入 `docs/TASKS.md (Status: blocked)` 并 `git commit` 退回给 Brain。
  - *注：在无需跨窗口/跨宿主的轻量级单会话场景中，Brain 与 Router 可由同一主会话兼任；一旦采用双环解耦，Brain 与 Router 必须职责分明。*

### 3. 为什么“工程代码自检”归 `Worker`，而 `Tester` 的唯一定位是“模拟真实用户”？
- **具体失败名称：“拿脚本 `ok: true` 当用户体验合格证” 与 “过度安全指令锁死 Tester 手脚”**。
- **真实翻车教训**：
  1. **代码脚本带偏 Tester**：当我们在交接单里把 `npm test`、类型检查或自动化 DOM 属性断言脚本写进 Tester 职责时，AI 会本能地选择最省力的“跑一遍脚本看退出码为 0”，而不再用眼睛去看真实界面——结果脚本全绿，但画面上封面下方粘着下一章标题、右上角按钮点出来的菜单跑到屏幕左下角、设置面板堆满反人类的内部参数，Tester 却给出了 `verified`。
  2. **过度防御规则锁死手脚**：当文档里写满“严禁覆盖数据、严禁抢占焦点、无法证明完全隔离就必须 blocked”等严厉教条时，负责任的 Tester 会花一个半小时去写快照备份、查进程树、算文件哈希，最后因为不敢碰界面而阻塞。
- **第一性原理切分（工程确定性 vs. 人类体验真实性）**：
  - **维度 A（工程契约自检 $\rightarrow$ 100% 归 Worker）**：类型检查、单元测试、架构守卫单测（Guard Tests）与构建打包，是 Worker 交卷前的分内前置条件（且不能用 `vm.runInContext` 这类脱离真实环境的假 UI 测试充数）。
  - **维度 B（模拟真实用户验收 $\rightarrow$ Tester 的唯一价值）**：怎么调试与验证，完全由产品形态决定，核心是模拟一个真实用户如何使用该产品——如果是 CLI 工具，Tester 就按用户手册敲命令看输出；如果是 GUI/Web/桌面插件，Tester 就像一个不懂技术的真实人类用户一样在专用测试沙盒里点按钮、滚轮翻页、拉宽窄窗口，并每一步截屏用视觉肉眼审视画面（排版美不美？图文有没有截断？弹出位置合不合直觉？文案是不是人话？）。测试沙盒本来就是供 Agent 随便点击和重置的游乐场，直接打开操作、看图挑刺即可，不搞快照备份或进程扫描等防御内耗。

### 4. 为什么 `Worker ≠ Tester`（唯一不可妥协的实现与验收隔离）
- **具体失败名称：“作者给自己发合格证”**。
- **不可溶解的信息差异**：Worker 在写代码的过程中，上下文里积累了大量“我为什么妥协、我为什么这么实现”的思维惯性。独立的 Tester 会话没有任何实现包袱，只站在真实用户与产品契约的视角去实际操作和审视产物，从而抓出作者视而不见的体验违和与真缺陷。

### 5. 为什么除了 Router、Worker 与 Tester，还需要按需派生的「一次性全新冷会话 `Auditor（逆熵铲屎官）`」？
- **具体失败名称：“长会话顺从腐化（Context Drift）” 与 “单任务局部贪心累积的慢性屎山（Local-Optima Slop）”**。
- **为什么现有的角色防不住慢性屎山？**
  1. `Brain` 和 `Router` 是常驻长会话，跑上几十轮后会产生顺从偏差与历史沉没成本包袱（觉得自己批过的方案都合理）；
  2. `Worker` 和 `Tester` 每次只盯着当前这 1 个任务：只要测试绿了、界面点得通就算过。但连续叠了 3~4 个任务后，代码里可能已经悄悄长出了多层包装函数、抠源码假测试或模块越界。
- **为什么 `Auditor` 由 `Router` 在睡前派生为一次性全新子代理，而不是由钩子另起后台进程？**
  1. **钩子里起的后台进程脆弱且抢资源**：它会随宿主 CLI 参数变化静默失败，还会与常驻 `Router` 争抢工作树与 `.git/index.lock`。由唯一消费者 `Router` 在排空全部 `pending` 里程碑后、休眠前检查水位线（自上次审计，即 `LESSONS.md` 首行 `reviewed-through` 之后，已结案不少于 2 个里程碑，或其间有里程碑跳过了 Tester），再派生一个全新的空白子代理 `Auditor`（审完即关），既保证零历史包袱，又让钩子只做唤醒、不与 Router 抢锁。
  2. **用「三大实证门槛」代替臃肿的二次确认（Proof over Second-Approval）**：如果给 Auditor 再配一个审批官，就会陷入“谁来监督监督者”的官僚死循环。根治之道是不让 Auditor 提任何主观风格建议，规定它只有拿到以下三类可证伪的物理铁证之一时才允许触发清创：
     - **破壁不红实证**：现场注释或改反被测核心业务代码跑测试，测试竟然仍 `PASS`（100% 坐实为假单测）；
     - **反模式行号实证**：精确指出 `filepath:line` 违反了明文禁止的套娃/截胡/假测试反模式；
     - **契约背叛实证**：精确指出代码行为（或 Brain 自己写的里程碑区块）违背了 `ARCHITECTURE.md / PRODUCT.md` 的哪一条。
  3. **当前回合当场铲平闭环**：`Auditor` 向 `Router` 返回实证缺陷后，`Router` 无需再改 `TASKS.md` 重新触发钩子，直接在当前回合派生新的 `Worker` 把屎山铲平，并按验收规则决定是否派 `Tester` 复验，最后把 `LESSONS.md` 的 `reviewed-through` 推到最新 `HEAD` 再休眠。

## Brain 与 Router 如何避免被细节淹没、避免并发丢单？

保持协调层轻量且无竞态的四条铁律：
1. **看摘要，不看代码**：Brain 与 Router 只读取结构化汇报和 `git log --oneline`，把冗长的代码编辑与测试日志隔离在 Worker / Tester 子会话中（Inline & Spill）。
2. **单文件滑动调度板（`docs/TASKS.md`）防 ABA 覆盖**：若调度文件只维护全局单一的 `Status: pending` 字段，当 Router 正在后台执行 `[Milestone #N]` 期间，人类与 Brain 讨论出 `[Milestone #N+1]` 并覆写文件，Router 在 `#N` 结束时大笔一挥改成 `Status: verified` 就会将 `#N+1` 静默覆盖吞掉。因此，`docs/TASKS.md` 内每个里程碑必须作为独立编号区块 `## [Milestone #N]` 维护各自的 `- **Status**: pending | verified | blocked | superseded`，各切片的 `Scope` 写在区块内：
   - **Brain 只追加/标废**：新任务追加在末尾；若推翻未完旧单，将其标为 `superseded (by #N+1)` 并追加新单；且提交时必须用 `git commit --only docs/TASKS.md` 防止把后台 Worker 的半成品代码误打包；
   - **滑动自净（Sliding Window GC）**：文件内仅保留未结案区块 + 最近 1~2 个已结案区块作为上下文锚点，更早的已结案区块在追加新单时顺手移出（完整历史留在 `git log` 中），确保单文件永远轻薄不膨胀。
3. **Router 精准核销与睡前排空循环（Drain-Loop Before Sleep）**：
   - Router 在 `#N` 验收通过准备改状态前，先重读 `docs/TASKS.md` 确认 `#N` 未被 Brain 标为 `superseded`，然后仅用精确 `edit` 修改 `## [Milestone #N]` 下的状态行；
   - **睡前排空自检**：即使宿主未将 Running 期间的新唤醒排队、或外部 Git Hook 对 `#N+1` 的唤醒信号因竞态丢失，Router 在提交完 `#N` 的 `verified`（以及睡前审计提交 `reviewed-through`）后、结束回合前，**必须再次读取 `docs/TASKS.md` 检查是否还有前置已满足的 `Status: pending` 里程碑区块**——若有，无需外部二次触发，直接在当前轮次继续执行下一单，直到没有可派发的 `pending` 才休眠。

## 为什么禁止“同一目录多子 Agent 碎任务并发”，而用“仓库内 `.tmp/worktrees/` 流水线重叠与正交并行”？

很多支持子 Agent 的宿主默认倾向于在**同一个目录**下将一个小需求拆成 3~5 个碎任务并发派发。这种“同目录表演式并发”在工程实践中效率极低，原因在于四重隐性税：
1. **冷启动重复阅读税（N × Context Tax）**：每个子 Agent 醒来都要重新读取同一批基础文件，Token 消耗翻 $N$ 倍。
2. **共享工作区踩踏（Workspace Contention）**：多个写操作子 Agent 在同一工作树并发改代码时，会互相覆盖公共入口，且一个子 Agent 的半成品代码会导致另一个子 Agent 的单测报错。
3. **语义撕裂与缝合税（Integration Tax）**：同一个业务切面被拆给互不通气的多个子 Agent 后，主控花在排查冲突和缝合上的时间远超直接串行写完。
4. **指令序列化开销**：写几百字 Prompt 交代上下文的时间往往比主会话直接执行 3 次 `edit` 慢数倍。

**真正的提速之道是「仓库内局部 Worktree（`<repo>/.tmp/worktrees/m<N>-s<K>`）+ 同一里程碑内的正交切片并行 + 主干线性收口」**：
- **草稿态与主干账本分离**：≤5 步 Fast Path 微调或上游契约冻结仍可直接单次干净提交到 `main`；完整里程碑/切片在本地短命分支或隔离 Worktree（拓扑 B 优先 Worktree，避免占用 `main` 主工作树影响 Brain 提交 `docs/TASKS.md`）中开发与多轮返工，本地分支不推远端。验收通过后按「最小可独立回滚语义单元」（单切片 = 1 条；多正交切片 = 每切片 1 条）Squash 线性合入 `main`，既杜绝 `wip:` 半成品与菱形 `merge commit` 污染主干账本，又保证每条 `main` 提交都能独立审计、`git bisect` 与安全 `revert`；同时严禁改写或强推已合入 `main` 的历史，落盘后立即删除 Worktree 与本地分支，分支腐烂硬冲突时基于最新 `main` 重放意图与守卫测试而非硬解旧冲突。
- **流水线重叠（验 `#N` 与写 `#N+1` 同时进行）默认关闭**：Tester 验收 `Milestone #N` 期间让 Worker 开工写 `#N+1`，会建立在尚未验收的代码之上；仅当 `#N+1` 与 `#N` 的 `Scope` 完全正交且上游共享契约已冻结时才开，此时 Router 在本仓库 `.tmp/worktrees/` 下为 `#N+1` 创建隔离工作树，消灭等待 Tester 的空窗期；
- **正交切片多路并行（2~3 路封顶）**：当同一里程碑内存在多个 `Scope`（写文件集）100% 物理正交、且上游共享契约已冻结的切片时，Router 为每个切片分配独立的 `.tmp/worktrees/m<N>-s<K>` 并行开发，待 Worker 各自跑通秒级内环单测并完成里程碑验收后，由 Router 按每切片 1 条原子提交 Squash 线性合回 `main` 并立即删除临时工作树与分支，做到互不串台、用完零残留。

## 调用频率：为什么协作单位是里程碑而不是任务

- **具体失败名称：“固定开销随任务数线性放大”**。上文的角色论证只回答了“谁要分开”，没有回答“多久跑一次”。每个任务各走一遍：Brain 派单提交、钩子唤醒、Worker 冷启动、Tester 验收、Router 结案提交、排空重读。Worker 在标准任务包上约 70~80 秒就能交卷（见 `docs/research/` 的 Worker 实测），而 Tester 的真实用户验收明显更慢，所以任务越碎，固定开销占比越高。这是据实测数据的推断，需要用真实项目的时间线确认。
- **信息差异不要求每个任务各验一次**。Worker 与 Tester 分开，靠的是 Tester 不带实现包袱的独立视角，这一点按里程碑验收同样成立。
- **里程碑** = 一条真实用户路径端到端走通、Tester 一轮就能判定的增量。**切片**是 Worker 的工作单位：Scope 重叠或有串行依赖的并成一个切片，Scope 正交才分开并行，不按文件或层拆碎。
- **改动单位变大后的三条配套规则**：
  1. Brain 要改未完成的里程碑，一律 `superseded` 后重发，不原地改写；Router 每次派切片前重读 `docs/TASKS.md`，发现被标废就停止派发，否则会在已作废的方向上白跑多个 Worker。
  2. 里程碑不验的情况只有一种：验收栏写“无”（不改变外部可观测表面）。此时独立性交给 Auditor，它本来就是全新会话、按批次审、只凭三类实证。
  3. 里程碑之间的先后只写在 `Depends-On` 字段里，不设排队状态。排队状态要求 Router 在结案提交里把后继改成 `pending`，这会新增 `pending` 行、经钩子再唤醒它自己一次，还多一种状态要维护；字段只在取单时判断，不产生额外提交。
- **代价**：缺陷归因变难（靠报告里的文件位置对回切片）；隐含依赖要到验收才暴露（所以同切面或 Scope 重叠的串行逻辑必须并成同一切片）；`Seen N×` 要按机制计，不按症状或打回次数计；流水线重叠默认关闭，因为会建立在未验证代码之上。切片 3~5 个封顶与 Auditor 默认每结案 2 个里程碑触发都是初始估计，没有实测数据。

## 角色生命周期：为什么只有 Router 常驻

- **具体失败名称：“Tester 变成熟练用户”与“用会话掩盖控制面缺口”**。
  1. 常驻 Tester 会熟悉产品、记住上一轮缺陷，渐渐对别扭的交互脱敏，这就是上文 Auditor 一节批评的长会话顺从腐化，只是搬到了 Tester 身上。所以 Tester 每个里程碑派生一个全新会话；同一里程碑内的返工复验沿用，因为它知道自己列过哪些问题。
  2. Worker 需要“我为什么这么写”的上下文只在返工时有用，所以保留到所在里程碑结案即可。跨里程碑的延续应当来自控制面（代码、commit body、`ARCHITECTURE.md`、`LESSONS.md`）；新 Worker 接不住，说明控制面有缺口，应补缺口，而不是留着会话。
- **提示缓存不是常驻的理由**。常驻会话的缓存命中率（见 `docs/research/dsh-native-agent-team-workflow.md`）只是成本收益，不影响时间或正确性，且依赖宿主的缓存存活期；里程碑之间间隔变长后，这笔收益本来就留不住。协议不依赖它，宿主命中了是红利。
- **Router 为什么仍常驻**：理由是单一消费者语义，正在运行时新唤醒排队，不会出现两个 Router 同时排空一个队列，而不是缓存。常驻带来的问题是它只在被唤醒时读一次协议，协议改了要等它休眠、再被唤醒才生效，所以 Router 每次取单前重读 `docs/ROLES.md`，改动在下一个里程碑生效。
- **Router 为什么只派生、不下场写代码**：下文 DeepSeek 消融里，单 Session 挂载 Subagent 工具时，5 次实验全是主模型自己硬干；退化的原因是结构上可以自己干，没有数据表明强模型对此免疫。同时 Router 握有 Worker 自检报告与 Tester 发现才能做打回分诊与 `LESSONS.md` 记账，自己写了代码就成了球员兼裁判，上下文也会被 diff 与日志塞满。

## 功能台账：为什么跳过 Tester 之后需要它

- **具体失败名称：“旧验收悄悄过期”**。验收栏写“无”的里程碑跳过 Tester，只靠 Commit Body 门禁证据与 Auditor 兜底。这两样只回答“这次改动对不对”，回答不了“之前验收过的用户能力现在还成立吗”。重构动到一条已验收能力时，自动化测试可能仍是全绿，体验却已经变了，而调度板结案就滑走，没有地方记这笔账。
- **台账把验收债写明**：里程碑的 `Features` 列出它推进或动到的条目；Tester 验过的行写新的验收提交，动到但没验的行降为 `待复验`。验收因此可以攒到用户可观测的里程碑或发布时一并做，不必每次内部改动都派 Tester，欠下的部分在台账里一眼可见。
- **发布是清债点**：发布前把范围内的 `待复验` 重新独立验收，人拿到的发布版本只建立在新鲜的验收上。
- **为什么是可选的**：台账每次结案要多同步几行，本身也要守卫测试防止失真。能力少、单宿主、不发版的项目，靠调度板和 `git log` 就能 1 分钟说清现状，不值得建。

## 缺陷归类：为什么按机制而不是按症状计数

- **具体失败名称：“同一缺口换个症状反复出现”**。一个隐含的模型缺失时（例如没有表格几何模型、身份存在文档之外），Tester 每轮都能在新的输入组合上撞到它：这一轮是图片被裁切，下一轮是标注与图片分页，再下一轮是嵌套表格溢出。按症状记账，每条 `Seen` 都停在 1×，“同一症状两轮”的止损从不触发；Worker 每轮补一个例子，晋升的守卫也只锁住见过的例子，直到里程碑因返工次数被迫升级。
- **按机制计数**：Router 打回时先回答“哪个隐含的模型或假设失效了”，同一机制的不同症状合并为一条。机制在同一里程碑内第二次出现，就说明补丁追不上输入空间，应当把模型写成显式、确定的实现，并用覆盖输入维度的矩阵测试替代逐例测试。
- **矩阵也交给 Tester**：Tester 的“一轮穷尽”依赖他知道该穷尽什么。里程碑写明矩阵维度，Tester 第一轮按矩阵全量覆盖，缺口一次暴露，而不是每轮多发现一个。

## 拓扑解耦：为什么同一协作内核适配“单宿主原生编排”与“跨窗口 Git 总线”

- **具体失败名称：“把旧宿主能力妥协层强加给新一代原生宿主”**。早期的跨窗口双环（独立常驻 Router + `docs/TASKS.md` 文件队列 + `.git/hooks/post-commit` 边沿唤醒）诞生于“思考窗口无法原生派生隔离子 Agent、独立工作树和浏览器代理”的宿主约束下。
- **内核与传输层分离**：
  1. **永恒不变的是协作内核**：Worker ≠ Tester 信息隔离、里程碑与正交切片防踩踏、按机制归类的 `LESSONS.md` 漏斗、`FEATURES.md` 验收债，以及实证门槛的冷会话 Auditor。无论在哪个宿主上跑，这些纪律都成立。
  2. **按宿主能力选择传输拓扑**：当宿主本身已原生具备子代理/Swarm、隔离工作树和浏览器代理时（**拓扑 A**），主会话直接兼任 Brain + Router，无需再搭建外部常驻会话和 Git Hook 总线；只有在跨软件/跨窗口异步派单或无人值守后台批处理场景下，才启用 **拓扑 B（Git 总线双环）**。

## 跨模型异源协作：为什么异源模型不应只当“事后审计员”，而日常 GUI Tester 留在原生宿主

- **具体失败名称：“同源盲区共振”“事后审计沉没成本锚定”与“跨工具 GUI 摩擦”**。
  1. 即使新开一个干净的同源冷会话，同一模型家族在架构偏好、调试假设、测试边界和 Fail-open 习惯上仍存在相关性盲区。但如果只把异源旗舰模型关在研发末尾充当“审 diff 质检员”，在 0→1 方案已经锚定、调试已经走入死胡同、同源测试已经定型之后才请它发言，就白白浪费了前 80% 最高杠杆的认知多样性。
  2. 因此协议把异源模型从单一 `Auditor` 解放为**全周期第二大脑与双向协作者（Cross-Model Peer）**：构思期双脑独立互搏去锚定、连续两次修不好时换脑冷排错破隧道视野、写测试前独立产出对抗边界矩阵、低频跳出 diff 做第一性架构拆骨体检、合并/发版前跑 0 噪音实证审计，并在显式隔离 Worktree 授权下支持硬核纯逻辑模块的双向互审（异源写、主力审）。
  3. 反之，日常 GUI/Web 体验验收强依赖浏览器交互与截屏闭环，硬塞给无浏览器能力的外部 CLI 只会制造高摩擦——这是**物理工具边界**，而非角色偏见，因此 GUI Tester 留在主宿主原生浏览器代理内完成效率最高。
  4. 无论多强的异源模型都会有误报或判断分歧，因此主控对只读报告必须逐条核实、对分歧交人裁决、对隔离写产出做反向全仓验证，绝不盲从。

## 理论溯源：DeepSeek《Super-agent 设计探索》的消融实验印证

DeepSeek Harness 团队在《Super-agent 设计探索：迈向更自主的 Agent 系统》中通过消融实验证明：
- **单 Session + Subagent 工具的退化陷阱**：在中性提示词下，给单个主 Session 挂载 Subagent 工具跑 20 项工作请求，**5 次实验中有 5 次主模型一次都没调用 Subagent，全在主 Session 里自己硬干**，导致 p95 耗时高达 **29.5 分钟**；而采用 **Router（只分派不干活）+ Worker（隔离执行）** 架构后，p50 降至 **12.4 分钟**、p95 降至 **15.7 分钟**。
- **提示缓存只是成本红利**：实测常驻会话的提示缓存命中率在 97% 以上（见 `docs/research/dsh-native-agent-team-workflow.md`）。协议现在只让 Router 常驻，Worker 与 Tester 按里程碑派生、结案即关，不依赖缓存命中。
