# 双环四重身份（Brain · Router · Worker · Tester）设计原理

## 第一性原理：什么时候才应该拆分角色？

**角色边界成立的唯一依据：合并它会产生一个可以说出名字的具体失败。**

在多 Agent 系统中，每增加一个角色就会增加一次“上下文转述损耗”和“协调开销”。
- **能力差异不是拆分理由**：同一个高水平模型既能做架构设计，也能写业务代码，还能做代码审查。
- **信息差异（Context Asymmetry）与交互对象差异（Human-Facing vs Unattended Automation）才是拆分理由**：当某一段上下文的存在本身会干扰另一项判断，或者一个会话是面向真人实时聊天、另一个会话是后台无人值守自动机时，才必须进行角色与会话隔离。

## 为什么完整形态是“双环四重身份”？（从三角色到四重身份的实测演进）

### 1. 为什么在宏观层 `Brain = Architect`（必须合并）
- **上下文同构**：宏观协调者与架构师需要完全相同的上下文——项目目标、产品审美、模块边界与关键技术决策。
- **唯一人类入口**：人只盯这 1 个窗口，和旗舰模型做高密度的思想碰撞，定稿后写入 `docs/TASKS.md (Status: pending)` 并执行 `git commit --only docs/TASKS.md`。

### 2. 为什么在执行环必须独立出 `Router（无人值守执行总控）`，而不能只写三角色？
- **具体失败名称：“后台会话身份迷失（停下来向空气提问）”**。
- **真实翻车机制**：
  - 当我们用 `.git/hooks/post-commit` 通过队列把自然语言消息（如 `"请读取并执行"`）塞进后台常驻的总控会话时，如果 `docs/ROLES.md` 里只写了 `Brain / Worker / Tester` 三角色；
  - 一旦独立 Tester 在验收时发现完成本任务目标必须连带修改某个同切面支撑文件（而任务包白名单漏列了该文件），Worker 不敢越权修改并上报给后台总控；
  - 此时后台总控看到自己身处一个聊天窗口、且刚收到一条 `user message`，**就会误以为对面坐着人类用户，直接在后台窗口里停下来礼貌提问：*“请问允许我扩大修改范围吗？”***——导致无人值守闭环当场卡死在没人看的后台窗口里！
- **立住 `Router`（第四重身份：执行环的战术总控与现场法官）的工程收益**：
  - 在 `ROLES.md` 与 Git Hook 唤醒消息（`[AUTO-WAKEUP] 你是无人值守 Execution Router...`）中明确宣告它的无人值守自动机身份：**它的触发源是 Git Hook，对面没有人类在看聊天框，严禁停下提问等待回复，更严禁沦为无脑传话筒拿显性 Bug 去打扰 Brain**；
  - 赋予 Router 明确的**战术自愈闭环权与 `LESSONS.md` 执笔权（显性问题不出执行环，战略冲突才报 Brain）**：
    1. **显性问题现场拍板**：当 Tester 发现实现/体验缺陷或完成本任务目标必需的同切面支撑文件漏列（未触碰禁区黑名单）时，Router 直接扩权支撑文件、指出根因方向（若连续 2 轮在同一症状打表层补丁则由 Router 介入重定根因重构方案），直接调度 Worker 修复并重跑 Tester；
    2. **执笔 `docs/LESSONS.md` 与 `Seen 3×` 守卫自进化**：Worker 视野局限在局部实现，Tester 视角是纯粹的不懂代码用户，**唯有 Router 同时握有“Worker 自检报告”与“Tester 翻车现场”**。因此每当发生 Tester 打回（说明残次品逃过了 Worker 的自检门禁），由 Router 亲自比对两边信息，将漏检模式写入或累加至 `docs/LESSONS.md (Seen N×)`；一旦某条显性工程规则达 `Seen 3×`，Router 当场指令 Worker 在返工时顺手将其写成 `tests/` 下的静态守卫单测（Guard Test），无需人类熬夜手动巡检即可完成防线自进化；
    3. **战略冲突升级**：仅当真正触及上游已冻结的公共契约自相矛盾、需求存在业务价值二义性需人类取舍、或连续 3 轮战术修复仍失败时，Router 才将完整证据写入 `docs/TASKS.md (Status: blocked)` 并 `git commit` 退回给 Brain。
  - *注：在无需跨窗口/跨宿主的轻量级单会话场景中，Brain 与 Router 可由同一主会话兼任；一旦采用双环解耦，Brain 与 Router 必须职责分明。*

### 3. 为什么“工程代码自检”归 `Worker`，而 `Tester` 的唯一定位是“模拟真实用户”？
- **具体失败名称：“拿脚本 `ok: true` 当用户体验合格证” 与 “过度安全指令锁死 Tester 手脚”**。
- **真实翻车教训**：
  1. **代码脚本带偏 Tester**：当我们在交接单里把 `npm test`、类型检查或自动化 DOM 属性断言脚本写进 Tester 职责时，AI 会本能地选择最省力的“跑一遍脚本看退出码为 0”，而不再用眼睛去看真实界面——结果脚本全绿，但画面上封面下方粘着下一章标题、右上角按钮点出来的菜单跑到屏幕左下角、设置面板堆满反人类的内部参数，Tester 却给出了 `verified`！
  2. **过度防御规则锁死手脚**：当文档里写满“严禁覆盖数据、严禁抢占焦点、无法证明完全隔离就必须 blocked”等严厉教条时，负责任的 Tester 会花一个半小时去写快照备份、查进程树、算文件哈希，最后因为不敢碰界面而阻塞。
- **第一性原理切分（工程确定性 vs. 人类体验真实性）**：
  - **维度 A（工程契约自检 $\rightarrow$ 100% 归 Worker）**：类型检查、单元测试、架构守卫单测（Guard Tests）与构建打包，是 Worker 交卷前的分内前置条件（且严禁 Worker 写 `vm.runInContext` 等脱离真实环境的假 UI 测试充数）。
  - **维度 B（模拟真实用户验收 $\rightarrow$ Tester 的唯一价值）**：**怎么调试与验证，完全由产品形态决定，核心是模拟一个真实用户如何使用该产品**——如果是 CLI 工具，Tester 就按用户手册敲命令看输出；如果是 GUI/Web/桌面插件，Tester 就像一个不懂技术的真实人类用户一样在专用测试沙盒里点按钮、滚轮翻页、拉宽窄窗口，并**每一步截屏用视觉肉眼审视画面**（排版美不美？图文有没有截断？弹出位置合不合直觉？文案是不是人话？）。测试沙盒本来就是供 Agent 随便点击和重置的游乐场，直接打开操作、看图挑刺即可，绝不搞快照备份或进程扫描等防御内耗。

### 4. 为什么 `Worker ≠ Tester`（唯一不可妥协的实现与验收隔离）
- **具体失败名称：“作者给自己发合格证”**。
- **不可溶解的信息差异**：Worker 在写代码的过程中，上下文里积累了大量“我为什么妥协、我为什么这么实现”的思维惯性。独立的 Tester 会话没有任何实现包袱，只站在真实用户与产品契约的视角去实际操作和审视产物，从而抓出作者视而不见的体验违和与真缺陷。

### 5. 为什么除了 4 个常驻热角色，还需要第 5 个「一次性全新冷会话 `Auditor（逆熵铲屎官）`」？
- **具体失败名称：“长会话顺从腐化（Context Drift）” 与 “单任务局部贪心累积的慢性屎山（Local-Optima Slop）”**。
- **为什么既存の 4 个热角色防不住慢性屎山？**
  1. `Brain` 和 `Router` 是常驻长会话，跑上几十轮后会产生顺从偏差与历史沉没成本包袱（觉得自己批过的方案都合理）；
  2. `Worker` 和 `Tester` 每次只盯着当前这 1 个任务：只要测试绿了、界面点得通就算过。但连续叠了 3~4 个任务后，代码里可能已经悄悄长出了多层包装函数、抠源码假测试或模块越界。
- **为什么 `Auditor` 必须由 `Router` 在睡前派生为「一次性全新冷子代理（Fresh Subagent）」，而不能在 Git Hook 里用 `nohup` 另起炉灶？**
  1. **告别场外进程竞争与 CLI 脆弱性**：若在 `.git/hooks/post-commit` 里用 `nohup` 拉起场外进程，不仅容易因宿主 CLI 参数升级静默崩溃，还会与常驻 `Router` 争抢工作树与 `.git/index.lock`。由唯一单消费者 `Router` 在排空全部 `pending` 任务后、休眠前检查水位线（距 `LESSONS.md` 首行 `reviewed-through` 累积 $\ge 5$ 个非文档代码提交）并直接派生一个**全新的空白子代理 `Auditor`**（审完即关），既保证了 **100% 零历史包袱冷启动**，又保持了 `.git/hooks/post-commit` 极简 8 行的纯粹与零锁冲突！
  2. **用「三大实证门槛」代替臃肿的二次确认（Proof over Second-Approval）**：如果给 Auditor 再配一个审批官，就会陷入“谁来监督监督者”的官僚死循环。根治之道是**严禁 Auditor 提任何主观风格建议，规定它只有拿到以下三类可证伪的物理铁证之一时才允许触发清创**：
     - **破壁不红实证**：现场注释或改反被测核心业务代码跑测试，测试竟然仍 `PASS`（100% 坐实为假单测）；
     - **反模式行号实证**：精确指出 `filepath:line` 违反了明文禁止的套娃/截胡/假测试反模式；
     - **契约背叛实证**：精确指出代码行为（或 Brain 自己写的任务单）违背了 `ARCHITECTURE.md / PRODUCT.md` 的哪一条。
  3. **当前回合当场铲平闭环**：`Auditor` 向 `Router` 返回实证缺陷后，`Router` 无需再改 `TASKS.md` 重新触发钩子，直接在当前回合命令 `Worker` 把屎山铲平 + `Tester` 复验，最后把 `LESSONS.md` 的 `reviewed-through` 推到最新 `HEAD` 安心休眠！

## Brain 与 Router 如何避免被细节淹没、避免并发丢单？

保持协调层轻量且无竞态的四条铁律：
1. **看摘要，不看代码**：Brain 与 Router 只读取结构化汇报和 `git log --oneline`，把冗长的代码编辑与测试日志隔离在 Worker / Tester 子会话中（Inline & Spill）。
2. **单文件滑动调度板（`docs/TASKS.md`）防 ABA 覆盖**：若调度文件只维护全局单一的 `Status: pending` 字段，当 Router 正在后台执行 `[Task #N]` 期间，人类与 Brain 讨论出 `[Task #N+1]` 并覆写文件，Router 在 `#N` 结束时大笔一挥改成 `Status: verified` 就会将 `#N+1` 静默覆盖吞掉。因此，`docs/TASKS.md` 内每个任务必须作为独立编号区块 `## [Task #N]` 维护各自的 `- **Status**: pending | verified | blocked | superseded` 与 `- **Scope**: ...`：
   - **Brain 只追加/标废**：新任务追加在末尾；若推翻未完旧单，将其标为 `superseded (by #N+1)` 并追加新单；且提交时必须用 `git commit --only docs/TASKS.md` 防止把后台 Worker 的半成品代码误打包；
   - **滑动自净（Sliding Window GC）**：文件内仅保留未结案区块 + 最近 1~2 个已结案区块作为上下文锚点，更早的已结案区块在追加新单时顺手移出（完整历史留在 `git log` 中），确保单文件永远轻薄不膨胀。
3. **Router 精准核销与睡前排空循环（Drain-Loop Before Sleep）**：
   - Router 在 `#N` 验收通过准备改状态前，先重读 `docs/TASKS.md` 确认 `#N` 未被 Brain 标为 `superseded`，然后仅用精确 `edit` 修改 `## [Task #N]` 下的状态行；
   - **睡前排空自检**：即使 Router 在执行 `#N` 期间因会话处于 Running 状态而错过了外部 Git Hook 对 `#N+1` 的唤醒信号，Router 在提交完 `#N` 的 `verified` 后、结束回合前，**必须再次读取 `docs/TASKS.md` 检查是否还有 `Status: pending` 的任务区块**——若有，无需外部二次触发，直接在当前轮次继续执行下一单，直到全文件 `pending` 彻底清零才休眠。

## 为什么禁止“同一目录多子 Agent 碎任务并发”，而用“仓库内 `.tmp/worktrees/` 流水线重叠与正交并行”？

很多支持子 Agent 的宿主默认倾向于在**同一个目录**下将一个小需求拆成 3~5 个碎任务并发派发。这种“同目录表演式并发”在工程实践中效率极低，原因在于四重隐性税：
1. **冷启动重复阅读税（N × Context Tax）**：每个子 Agent 醒来都要重新读取同一批基础文件，Token 消耗翻 $N$ 倍。
2. **共享工作区踩踏（Workspace Contention）**：多个写操作子 Agent 在同一工作树并发改代码时，会互相覆盖公共入口，且一个子 Agent 的半成品代码会导致另一个子 Agent 的单测报错。
3. **语义撕裂与缝合税（Integration Tax）**：同一个业务切面被拆给互不通气的多个子 Agent 后，主控花在排查冲突和缝合上的时间远超直接串行写完。
4. **指令序列化开销**：写几百字 Prompt 交代上下文的时间往往比主会话直接执行 3 次 `edit` 慢数倍。

**真正的提速之道是「仓库内局部 Worktree（`<repo>/.tmp/worktrees/task-<ID>`）+ 流水线重叠（Pipelining）」**：
- **单任务零开销**：队列只有 1 个任务且主目录空闲时，直接在主工作树执行（Write = `1`）；
- **流水线重叠（验 `#N` 与写 `#N+1` 同时进行）**：当 Tester 正在主工作树耗时做真实界面视觉验收 `Task #N` 时，若队列里已有 `Task #N+1`，Router 立即在本仓库 `.tmp/worktrees/task-<N+1>` 下创建隔离工作树（软链复用 `node_modules/.venv`），让 Worker 同时开工写 `#N+1`，彻底消灭等待 Tester 的空窗期；
- **正交切面多路并行（2~3 路封顶）**：当 `docs/TASKS.md` 中存在多个 `Scope`（写文件集）100% 物理正交且上游共享契约已冻结的完整垂直任务时，Router 为每单分配独立的 `.tmp/worktrees/task-<ID>` 并行开发，待 Worker 各自跑通秒级内环单测后由 Router 变基快进合回 `main`（`git rebase main && git merge --ff-only`）并立即 `git worktree remove --force` 销毁临时目录，做到多项目互不串台、用完零残留。

## 理论溯源：DeepSeek《Super-agent 设计探索》的消融实验印证

DeepSeek Harness 团队在《Super-agent 设计探索：迈向更自主的 Agent 系统》中通过消融实验证明：
- **单 Session + Subagent 工具的退化陷阱**：在中性提示词下，给单个主 Session 挂载 Subagent 工具跑 20 项工作请求，**5 次实验中有 5 次主模型一次都没调用 Subagent，全在主 Session 里自己硬干**，导致 p95 耗时高达 **29.5 分钟**；而采用 **Router（只分派不干活）+ Worker（隔离执行）** 架构后，p50 降至 **12.4 分钟**、p95 降至 **15.7 分钟**。
- **订阅直通（省下 37% 读缓存 Token）与算力热驻留**：同一项目连续波次的后续任务直接发往已驻留的具名 Teammate（Warm Router / Worker / Tester），在真机实测中拿到了 **97.75% ~ 98.62%** 的 KV Prompt Cache 命中率。
