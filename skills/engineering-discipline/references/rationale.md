# 工程与验证纪律设计原理

本文件解释 [SKILL.md](../SKILL.md) 中各项工程红线与验证纪律背后的成因与取舍。执行步骤、铁律与检查清单以 SKILL.md 为准。

## 一、为什么工具选择要区分“执行选最轻”与“验收选最真”

日常实现和调试追求的是**反馈速度与确定性**：API / SDK（L1）和 CLI / 测试运行器（L2）毫秒到秒级返回结构化结果，远优于缓慢易脆的 GUI 点击。

但用户体验验收的方向正好相反。AI 在验收阶段有强烈的省力倾向——只要交接单或习惯允许，它往往只跑一遍测试脚本或 DOM 属性断言，看到退出码为 0 或 `ok: true` 就放行，结果真实画面里文字截断、弹层飞位、按钮重叠全部漏过。因此交付物只要包含用户可见界面，验收必须直达 L4（真实渲染表面操作 + 截屏肉眼审视），下层脚本绿灯不能代替上层感官验证。

## 二、为什么双速回路、UI 自拍看镜子与实验台先行（Harness-First）缺一不可

1. **秒级无头内环 vs 终点真实外环**：如果在改算法、布局计算或状态机时每改一行都打包重型客户端或跑分钟级 E2E，Agent 的迭代吞吐会崩塌。将 80%~95% 的核心逻辑抽离为可离线仿真的纯逻辑内核（Functional / Simulatable Core），在 `<1~3s` 内跑完无头单测，把慢速真实环境验收留到里程碑终点跑一次，才能同时拿到速度与真实性。
2. **为什么 Worker 交卷前必须“自拍看镜子”**：大模型的文本编码能力与像素视觉判断分属不同通道——代码里少一个 CSS 属性或错一个坐标，单测全绿，但看一眼真实截图 1 秒就能发现穿帮。Worker 交卷前自截 1~3 张图并用图像工具亲自看一遍，把明显视觉缺陷消灭在进入 Tester 返工循环之前。
3. **为什么必须实验台先行（Harness-First）**：当运行环境对 Agent 是黑盒（例如 GUI 弹窗报错但进程退出码为 0、重型引擎必须人工点编辑器才能跑一轮），Agent 只能靠盲猜叠补丁。先把异常直出文本、CLI 状态自省入口和一键冒烟脚本打通，等于先给 Agent 装上眼睛。
4. **三面独立互证**：只看单一信号极易产生假阳性（进程退出码 0 但业务数据没落盘、HTTP 200 但响应体是错误包装）。把“通过正式入口行动”“用只读手段观察内部状态”“按业务契约判定结果”三者解耦，才能避免测试后门与自欺欺人。

## 三、为什么防御式编码重点打击“隐式兜底、延时碰运气与套娃包装”

1. **时序不靠 `sleep` / `setTimeout(0)`**：用固定延时或让出一次事件循环等待异步就绪，在快机器上偶发通过、在负载变化时随机雪崩，掩盖了真实的状态机或事件订阅缺失。
2. **禁止多层可选链兜底与单值混代**：一长串 `a?.b?.c ?? "默认值"` 把上游契约缺失静默吞成了看似合法的业务值；而把“尚未查询（`unknown`）”“查询结果为空（`empty`）”“具体值（`value`）”都塞进 `null / undefined`，会让下游无法区分故障与空集。
3. **禁止同名包装与事件截胡**：AI 在不敢动旧代码时习惯保留原函数、在外层写 `fnBase = fn; fn = ...` 套娃，或另挂监听器截胡旧事件，或把节点渲染到错位再挪走。这会制造隐形多层状态和难以定位的幽灵副作用，必须直接重构原函数并删净旧逻辑。
4. **为什么既禁止 `_backup` 垃圾，又严格保护未提交工作现场**：已提交源码有 Git 历史兜底，`.gitignore` 测试沙盒随时可重建，留 `_old` / `_backup` 或写备份脚本/进程扫描纯属内耗；但工作区中他人或先前会话留下的未提交改动和未跟踪本地夹具不受 Git 保护，一旦误删不可恢复，因此动手前必查 `git status`。

## 四、为什么反 AI Slop 单测四铁律能根治“为绿而绿”

AI 写测试最常见的三种失效模式：
1. **恒真假测试（Tautological Tests）**：断言太松或测偏了分支，哪怕把被测核心业务代码注释掉，测试依然绿灯。**手动破壁验证（`Broken by hand, each red`）**把“把代码改坏 → 确认测试报红 → 恢复变绿”变成硬前置，直接消灭恒真测试。
2. **Mock 测 Mock / 抠源码字符串**：把内部协作模块全 Mock 掉，结果只是在验证自己写死的 Mock 返回值；或者用 `readFile("src/...")` 配正则、`eval` / `vm.runInContext` 跑脱离真实环境的假 UI 测试，源码一重构就形同虚设。常规测试应跑通真实模块导出与内部状态流转，只在进程外边界使用受控替身。
3. **只跑局部包漏掉跨模块守卫**：架构守卫单测与跨包契约常分布在未直接修改的包里，交卷前必须跑全仓测试套件；且任何既有红灯都是当前必须处理或立项的缺陷，不能以“main 上原本就红”为由带病合入。

能用代码静态扫描或反射锁死的架构红线，写成 `tests/` 下的守卫单测随套件自动执行，远比写在 Markdown 里靠 Agent 自觉可靠。

## 五、为什么架构推崇垂直单向 DAG、显式组装与 AI-Native 选型剃刀

1. **旧时代妥协层 vs 真领域底座**：前 AI 时代的许多重型中间层（厚重 ORM、跨端套壳桥接、为了 80 行逻辑引入外部黑盒包）是为了迁就人类手写代码慢与记忆带宽低。在 AI 将语法转译与样板编写成本压低后，应全力借力封装客观物理/数学复杂度的领域底座（数据库引擎、原生 UI、物理/渲染引擎），同时剥离横亘在中间、降低可观测性的黑盒胶水；100~200 行内可完成的功能直接写零依赖代码。
2. **垂直高内聚小包优于 `service / handler / repository / util` 水平分层**：按技术工种水平分包会把数百个不相关文件塞进同一命名空间，改一个小需求跨四五个目录跳跃，上下文碎片化严重；按业务领域或物理机制垂直切分、强制外层向纯逻辑内核的单向无环依赖（DAG），既缩小单次改动视野，又便于用守卫单测锁死边界。
3. **保留 DI 模式、砍掉 DI 框架**：通过构造函数显式传参能保证可测试性；但自动反射或代码生成 DI 容器会掩盖“一个服务依赖十几个组件”的上帝对象，并切断静态调用链追踪。在 `main` 显式组装依赖，一旦构造函数参数超过 5~6 个，腐败臭味立刻暴露，迫使团队按职责垂直拆分。
4. **变化率物理隔离**：将高确定性的纯逻辑内核与高频突变的第三方协议/外部渠道适配物理拆包隔离，并把长尾易腐模块沉淀为可插拔边缘，保证内核长期稳定且可在内存仿真底座上毫秒级自测。

## 六、为什么“文档保持纯净现在时，Commit Body 作永久验证账本”

如果在代码注释和架构文档里写满“之前用 X 会报错所以改成 Y”“（已实现！）”或迁移待办清单，文档会迅速腐败并误导后续新会话的 Agent。把“当前是什么、有哪些不变量与失败契约”以现在时态留在代码注释和薄架构文档里，同时把“为什么改、根因是什么、怎么破壁验证的、哪些边界未覆盖”轻量写入 Git Commit Body，既实现内部重构零文档税，又能通过 `git log / git blame` 永久审计历史脉络。
