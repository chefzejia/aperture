# 工程与验证纪律 Skill

## 核心原则

1. **契约规定目标，源码与运行结果说明当前事实**：两者不一致时定位根因，绝不通过篡改契约或放宽测试把缺陷伪装成正确。
2. **共同可观测，不维护隐式状态**：判断、修改和验证证据必须对人直接可见，不在不透明缓存或临时脚本里藏匿状态。
3. **找根因，不打表层补丁**：连续两次对同一症状打局部补丁仍未解决，说明根因未找到，必须停下来重新推演。

## 工具选择梯度（操作选最轻，验收选最真）

工具选择必须严格区分**「日常执行/自动化操作」**与**「用户体验验收」**两个方向相反的场景，严禁混用：

```text
L1 结构化接口：服务自身的 API / SDK / 原生结构化工具
L2 确定性 CLI：git、curl、构建工具、测试运行器、编译器等命令行
L3 脚本化驱动：浏览器 DOM/网络自动化脚本、客户端驱动协议
L4 用户感官表面：真实窗口点按交互 + 视觉截图肉眼审视（Human-Like UI Inspection）
```

1. **日常操作、构建与逻辑自检（从轻到重：`L1 → L2 → L3`）**：
   - 读写数据、跑单测、查日志或执行批处理时，优先选最轻、最确定的一级（有 L1/L2 绝不盲目动用慢速 GUI 点击）。
2. **产品与用户体验验收（直达真实用户表面：强制匹配产品交付层）**：
   - **严禁拿底层的 `L1/L2` 脚本绿灯去替代顶层 `L4` 的真实用户体验验收**！如果交付物是 GUI、网页或客户端界面，独立验收（Tester）必须直接在真实渲染出的界面上像人类用户一样操作并**截屏用肉眼审视画面**（排版、对齐、遮挡、截断、文案），绝不能因为“不想跳级到 L4”而只跑个 CLI 脚本或 DOM 属性断言就宣称界面正常。
3. **断言“环境不具备某能力”前必须先实测**，区分“未配置”与“宿主不支持”，不静默跳过验证。

## 子 Agent 派发纪律（摘要）

子 Agent 不是免费的多线程，每次派发都会产生冷启动重复阅读税与共享工作区踩踏风险。完整的角色协议（Brain · Router · Worker · Tester）与并发配额以 `multi-agent-collab` Skill 为唯一权威事实源，日常执行谨记三条硬边界：

1. **Fast Path（`0` 子 Agent）vs Slow Path（必派 Worker/Tester）**：$\le 5$ 步工具调用的局部微调或上游契约冻结由主会话直办；完整业务模块实现、跨多文件重构或独立验收必须下沉至隔离的 Worker 与 Tester。
2. **写操作（Write / Edit）单工作区并发上限 = `1`**：同一共享工作树同一时刻最多只允许 `1` 个活跃写 Agent；仅当满足 **① 独立 Git Worktree**、**② 写文件集 100% 物理正交**、且 **③ 共享 Schema 已提前冻结**时，才允许按完整垂直模块并行写（上限 $\le 3$ 个）。
3. **只读操作（Read / Explore / Audit）并发上限 = `2 ~ 4`**：按正交子系统或独立审查维度扇出，禁止按零碎单文件拆出大批子 Agent。

## 变更与防御式编码纪律（13 条铁律）

1. **精确覆盖范围**：说清哪些情况变了、哪些相邻情况没变，不同性质的错误不混作同一种兜底。
2. **到达所有同类位置（Reach Every Sibling）**：修一处缺陷后全局检索同构模式（同类调用点、子命令、守卫），在同一变更内一并修复。
3. **重推导下游依赖**：改了公式、数据结构、布局或时序，必须找出所有假设旧语义的调用方、缓存和测试并重新验证。
4. **读失败即未知（Fail-closed）**：读取、解析或校验失败时，结果是“未知”而非“空/无/相等”；安全与权限守卫遇到读取失败必须拒绝放行。
5. **预览零副作用**：`dry-run`、`plan`、`preview` 等只读操作绝不写入任何持久或临时状态。
6. **错误分类窄化**：一个错误码或异常标记只对应它精确描述的那一种失败，不吞掉未知异常。
7. **外部系统取值溯源**：对接外部系统或协议时，字段类型与取值从该系统的官方契约或二进制实测中获取，不凭字段名臆测。
8. **时序不承载异步就绪猜测（No Readiness-by-Sleep）**：异步就绪与状态同步必须来自显式的调用顺序、事件通知或状态机（协议规范或硬件时序明确要求的固定退避/采样延时除外），**严禁用 `setTimeout(..., 0)`、`queueMicrotask` 或拍脑袋的固定 `sleep` 碰运气等待渲染/异步状态就绪**。
9. **锁内禁无界阻塞与并发状态隔离（No Unbounded Blocking Under Lock & Race-Free State）**：持有互斥锁时，**严禁在锁内发起无界网络/磁盘 I/O 等待或调用可能产生死锁的阻塞操作**；共享可变状态必须在移交并发读取前完成初始化，且警惕浅拷贝包含嵌套引用（如字典/映射、数组/切片或对象指针）的数据结构；任何新增后台任务、定时器或并发共享状态的变更必须跑通所在语言/平台的竞态检测（如 `go test -race`、TSan 或并发压力测试）。
10. **可选输入显式声明双分支（No `?.` Fallback Chains）**：严禁堆叠 `a?.b?.c?.d ?? fallback` 掩盖契约缺失；可选参数必须在接口契约中同时规定“存在时”与“缺省时”的确定性行为。
11. **单值单语义（One Value States One Fact）**：“尚未查询（`unknown`）”、“查询结果为空（`empty`）”与“具体值（`value`）”是三种不同事实，必须用可辨识联合类型（Discriminated Union）或显式枚举区分，严禁用单一 `null / undefined` 混代多种语义。
12. **直接重构原函数，严禁套娃包装与死代码截胡（No Wrapper Monkey-Patching）**：修改既有函数或组件行为时，必须直接修改原函数定义并删净旧逻辑；**严禁因为怕改坏旧代码而保留原函数不动、在外层写 `const fnBase = fn; fn = ...` 同名重赋值套娃，或用 `stopImmediatePropagation()` 截胡屏蔽未删除的旧事件监听器，或先渲染到错误容器再用 `append` 拔节点搬家**。
13. **Git 保障已提交历史，严禁防御性快照垃圾但须保护未提交工作现场**：仓库内已提交代码的回滚安全由 Git 保障，**严禁在源码里留存 `_old / _backup` 废弃实现，也严禁对已明确可重建的专用测试沙盒编写 `*-backup-*` 目录拷贝或全局进程扫描代码**；但修改或清理前必须先检查 `git status`，**严禁擅自覆盖、回滚或清除工作区中他人或先前会话留下的未提交修改（Uncommitted / Untracked Work）与不可重建的本地夹具**。

## 代码注释、文档去噪与 Commit Body 审计账本

1. **代码与文档只写契约，不写心路历程（No Reasoning Transcripts）**：注释、JSDoc 和长期文档只陈述**类型签名与代码结构无法表达的契约**（前置/后置条件、不变量、所有权、并发锁序、反直觉失败行为），并指名函数符号而非易过期的行号。**严禁把调试推理过程（“之前用 X 会报错所以改成 Y”）、步骤旁白或复盘流水账写进代码注释或架构文档。**
2. **已落地文档一律用现在时（Present-Tense Only）**：功能或决策合入后，文档只描述**系统当前如何工作**；严禁残留 `should`、未来计划、迁移待办清单或 `"（已实现！）"` 等易腐状态词。
3. **内部重构零文档税**：文档只链接源码文件与符号名，不抄录常变的实现细节；只要对外职责、状态流转和失败契约未变，内部重构无需修改文档。
4. **Commit Body 即永久验证账本（Commit Body as Audit Ledger）**：代码与架构文档保持纯净现在时，`docs/TASKS.md` 滑动清理；**“为什么改、怎么验证的”必须按变更性质轻量沉淀在 Git Commit 中**，供日后 `git blame / git log` 追溯：
   - **Commit Subject（标题行）**：点明修改的模块前缀，用平实语言陈述**用户或调用方现在可观测到的行为变化**（如 `gateway: treat 429 with spent-balance body as out-of-credit, not rate-limit`），拒绝空洞的 `fix bug` 或 `update code`。
   - **Commit Body（正文段落，按需轻量记录，拒绝八股文）**：实质性功能、修复或重构提交在正文中简明记录三件事：① **意图或根因（Why / Root Cause）**（新功能的设计边界，或 Bug 的触发根因、修复机制及同步覆盖的同类位置 Siblings）；② **验证证据（Verification）**（实际运行的测试命令与结果；涉及核心逻辑或修 Bug 时，说明如何通过**手动破壁 `Broken by hand`** 确认测试在破坏被测分支时会精准报红）；③ **未覆盖边界（Not tried，如有）**（受环境限制诚实未覆盖的验证项）。

## 双速调试回路、UI 自拍看镜子与实验台先行纪律（Two-Speed Loop, Self-Screenshot Check & Harness-First）

1. **双速调试回路（秒级无头内环 $\rightarrow$ UI 交卷自拍看镜子 $\rightarrow$ 终点真实外环）**：
   - **内环（Worker 高频调试回路，目标 `< 1~3s`）**：95% 的算法、分栏几何计算、路由解析、状态流转与协议校验必须在**零 GUI 启动开销的纯函数或内存无头（Headless）测试**中闭环。严禁每改一行代码都去打包重型客户端、重启浏览器或跑分钟级 E2E 慢速试错。
   - **UI 交卷前「自拍看镜子」（Worker Capture & Read-Image Before Hand-off）**：凡涉及前端、客户端、图表或样式排版的修改，Worker 在无头单测跑绿后、**交卷给下游前，必须自己对改动后的真实渲染表面截 1~3 张关键状态图（存入 `.tmp/evidence/task-<ID>/`），并亲自调用图像查看工具（`read_image / view_image`）用自己的多模态眼睛审视一遍**！把大模型的“文本编码脑”与“像素视觉脑”在交卷前短路接通，当场顺手修掉单测查不出的按钮重复、文字重叠、弹层飞位或颜色错乱，避免带着低级视觉穿帮进入下游打回循环。
   - **外环（Tester 真实用户终验 + 可视化证据归档，每单仅在终点跑 1 次）**：Tester 在真实客户端/浏览器中完成独立盲测与挑刺后，将最终通过验收的关键截图（或对比展示页）保留在 `.tmp/evidence/task-<ID>/` 并在任务单验收摘要中附上路径，供人类无需启动应用即可在 3 秒内扫一眼图片完成最终审美把关（Taste）。
2. **实验台先行（Harness-First：先让 Agent 看见，再写业务代码）**：
   - 严禁在 Agent 处于“致盲状态”（如 GUI 弹窗报错但终端退出码为 0、重型引擎需手动点开编辑器才能跑完一轮）时盲猜堆砌补丁。在编写复杂业务或跨平台/游戏引擎功能前，必须先打通三条自动化感官管道：
     - **异常与状态直出文本（Crash & State to Stdout/Log）**：全局捕获未处理异常、渲染错误与关键状态迁移，以结构化纯文本落盘或直出终端，杜绝静默吞错或仅弹图形对话框；
     - **开发期状态自省入口（CLI State Inspection）**：提供可由命令行或测试直接触发的状态导出开关（如 `--dev-dump-state` 或无头仿真入口），让 Agent 无需截图即可毫秒级核对内部状态树；
     - **一键冒烟闭环脚本（One-Shot Smoke Script）**：将“构建 $\rightarrow$ 沙盒启动 $\rightarrow$ 触发动作 $\rightarrow$ 收集日志/截图 $\rightarrow$ 清理退出”封装为单条确定性命令。
3. **三面独立互证（Three-Surface Cross-Check）**：
   排查问题时，三个观察面必须独立校验，不依赖单一信号：
   - **行动面**：通过正式入口推进（公开 API、CLI、真实 UI），不为凑测试而在生产代码里开后门。
   - **观察面**：用只读证据判断系统内部发生了什么（日志、进程状态、数据库只读查询），观察动作本身不制造新状态。
   - **判定面**：对照业务契约检查最终结果，**进程退出码为 0、HTTP 200 或日志无报错不能单独作为成功证据**。

**根因定位公式**（先保留失败现场，写出可证伪的结论再改代码）：
> 当 `<触发条件>` 发生时，`<责任模块>` 因为 `<错误机制>` 未能完成 `<应尽职责>`，导致用户观测到 `<表面症状>`。

## 验证分层、反 AI Slop 单测铁律与测试隔离

验证按层次递进，下层通过不能替代上层验收：

```text
静态检查（Typecheck / Lint） → 单元测试 & 架构守卫单测（Guard Tests） → 集成测试（真实依赖/持久化） → E2E 验收（正式入口 + 真实数据流）
```

- **架构规则优先写成守卫单测（Guard Tests over Prose Warnings）**：凡能用代码静态扫描或反射锁死的架构红线（如“核心包禁止 import 插件”、“禁止裸调 `exec.Command`”、“禁止同名函数 `fnBase = fn` 重赋值套娃”、“禁止抠源码字符串跑假测试”、“配置项与 Schema 必须同步”），**必须直接写成 `tests/` 下的守卫单测随测试套件自动执行**，绝不只写在 Markdown 里靠 Agent 自觉。
- **根治“为绿而绿”的 AI Slop 单测四铁律**：
  1. **手动破壁验证（Broken by Hand, Each Red）**：任何新增或修改的核心行为测试，必须通过**手动破坏其声称保护的关键业务分支（如反转核心条件、注释关键状态更新、丢弃关键字段）**来证明其敏感性——每次破坏后运行测试必须精准报红（`FAIL`），再恢复代码变绿。把被测核心逻辑改坏后依然 `PASS` 的恒真测试（Tautological Test）必须当场删除或重写。
  2. **边界替身优先，拒绝无意义的内部 Mock（Boundary Fakes over Internal Mocks）**：**严禁用 `readFile("src/...")` 截取源码字符串塞进正则或 `eval / vm.runInContext` 中跑假单测，也禁止在普通业务逻辑测试中把内部协作模块全部 Mock 掉去“测自己的 Mock 返回值”**。常规测试应调用真实的模块导出入口并跑通内部状态流转，在进程外边界（如第三方 HTTP 接口、外部时钟/文件系统）使用受控测试替身（仅在注入底层硬件/I/O 确定性故障或极端竞态时才允许局部接口替身，且须显式声明证明边界）。
  3. **真实故障字节优先 + 表驱动边界覆盖（Literal Bytes & Table-Driven Boundaries）**：涉及外部协议兼容、历史线上故障修复或第三方响应解析时，优先使用**真实抓包保存的原始字节流**建立回归夹具；对于全新协议或算法实现，结合真实规范样本与紧凑的**表驱动边界/性质测试（Table-Driven / Property Tests：覆盖缺失字段、空值、截断块与极值）**，不在强类型语言中为编译器已静态拦截的非法类型堆砌冗余单测。
  4. **全仓测试门禁，严禁只跑局部改动包（Full-Suite Gate）**：由于架构守卫单测与跨模块契约分布在未直接修改的包中，交卷前必须运行全量测试套件（如 `go test ./...`、`pnpm test`）及静态检查，且主干上任何既有红灯都是当前必须修复或立项的真实缺陷（严禁以“原本在 main 上也是红的”为由带病合入）。
- **工程自检（Worker）与模拟真实用户验收（Tester）职责分离**：代码单测、破壁验证与全仓构建门禁由实现者（Worker）100% 跑通；独立验收（Tester）不写单测脚本，而是按产品交付形态模拟真实人类用户操作与视觉审视，并在首轮一次性穷尽可见缺陷（完整协作契约见 `multi-agent-collab` Skill）。
- **测试沙盒直接复用、零防御内耗**：单测在临时目录/沙盒 HOME 下运行，严禁触碰宿主机真实用户配置或发起真实公网请求；项目内已列入 `.gitignore` 的专用测试沙盒（如 `.tmp/`）直接读写使用，**严禁编写快照备份、进程树扫描、文件哈希比对等过度防御代码**。
- **链式命令防吞错**：管道验证必须开启 `set -o pipefail`，防止前置测试失败被后续命令掩盖。

## 架构加减法与 AI-Native 选型剃刀（Eliminate Human-Bandwidth Compromises）

**第一性原理**：过去许多主流框架、水平分层与黑盒库，并非物理或数学上的最优解，而是为了迁就“人类手写代码慢、记忆带宽低、手写组装烦”而发明的**人类带宽妥协层**。当 AI 将语法转译、几何计算与样板编写成本压近于 $0$ 时，每次技术选型、分包或设计方案前，遵循五条极简准则：

1. **第一性原理三问（每次引入框架/库/抽象前必问）**：
   - **质疑妥协性**：这个方案之所以流行，是因为它在物理性能与最终体验上真的最优，还是仅仅因为过去人类手写太慢而找的“拐杖”？
   - **探寻原生解**：如果不考虑人手敲代码累不累，这个问题在**底层系统、数学几何或关系代数上最纯粹、最直接的原生解法**是什么？
   - **追求形式化确定性**：严苛的编译器与强类型契约对人是负担，对 Agent 却是**免费的实时强化学习反馈护栏**——永远优先选择编译期最严格、状态最显式的技术栈（如显式数学坐标优于隐式盒模型盲猜，强类型编译器优于动态弱类型）。
2. **垂直高内聚小包与单向无环依赖（DAG），严禁水平技术分层与垃圾桶包（Vertical Subsystems over Horizontal Layer Slop）**：
   - **拒绝 `service / handler / repository / util` 水平大泥球**：按技术工种水平分包会导致单个 `service` 包塞入数百个文件（包内私有状态对所有模块裸奔）且改一个需求需跨 5 个目录跳跃。必须按**“它解决什么独立业务领域或底层物理机制”**切分垂直高内聚小包，严禁建立语义宽泛的 `utils / helpers / common / managers` 垃圾桶包。
   - **单向无环依赖树（Acyclic DAG，具体层级由项目 `ARCHITECTURE.md` 定义）**：垂直包之间绝非平行网状互调，必须遵循自上而下或外层向内核的**单向无环依赖（DAG）**——零外部 I/O 的纯领域/逻辑内核与底层原语处于最下层（最内层），业务编排、外部协议适配与用户交互外壳处于上层（外层），并用静态守卫单测锁死依赖方向，严禁反向依赖或循环依赖。
3. **保留依赖注入模式，砍掉 DI 容器与代码生成胶水（Explicit Wiring over DI Frameworks）**：
   - **使用依赖注入模式（DI Pattern）**：模块通过构造函数显式接收所需接口或结构体参数，不在内部硬编码全局单例，以便测试注入替身。
   - **禁止引入 DI 框架/IoC 容器（No `wire / fx / Spring IoC / TSyringe`）**：自动代码生成或反射注入容器会掩盖“一个服务依赖 14 个组件”的上帝对象腐败臭味，并切断静态调用链追踪。必须在程序入口（`main`）用几十行代码显式手动组装依赖图；**一旦某个构造函数参数超过 5~6 个，说明模块职责不纯，必须立即垂直拆分子系统，而非引入 DI 框架掩耳盗铃**。
4. **可仿真纯内核、变化率物理隔离与跨端对齐（Simulatable Core, Volatile Edge & Cross-Platform Sync）**：
   - **真领域底座借力 vs 可离线仿真纯内核（Functional Core, Imperative Shell）**：全力借力客观物理/数学底座（如 Unity/Unreal 渲染物理引擎、SQLite/DuckDB、OS 原生 UI），但必须将 80%+ 的核心业务规则、数值公式与状态机剥离为**零重型引擎/零外部 I/O 依赖的纯文本逻辑内核（Simulatable Core）**，配合成熟的内存级仿真替身（如内存文件系统、内存 SQLite、无头战斗仿真），使核心逻辑无需启动重型 GUI/编辑器即可毫秒级单测；二进制资产（如 `.uasset` 蓝图、Prefab、XAML/Storyboard）仅作最薄的视觉挂载壳。
   - **高确定性 Core 与高变动 Edge 隔离**：核心状态机/账本/路由与高频突变的第三方逆向协议/外部渠道适配必须物理拆包或通过插件宿主隔离；低频控制面跨语言优先走纯文本/JSON 极窄边界，高频热路径（如游戏帧循环）留在同内存空间或走 C-ABI 零拷贝。
   - **跨端契约共享与精度分级**：多端 UI 与宿主交互层共享 `PRODUCT.md`、设计 Token 与同步对账表（记录基准 Commit 水位线与刻意差异理由），由各端原生语言独立展开；要求 bit-for-bit 绝对一致的算法内核则通过编译二进制库跨端共享。
5. **内部删除优于兼容**：
   - 单一场景直接实现，第二个真实用例出现时再抽象；内部重构直接删除废弃代码与旧路径，不堆砌内部兼容层（对外公开协议除外）。

## 停止与升级规则（人机边界）

遇到以下任一情况，立即停止自主修改并交由人裁定：
1. **改变对外承诺**：需缩减功能范围、修改公开 API 契约、变更持久化数据格式或降低性能/安全指标；
2. **不可逆生产/外部操作风险**：涉及删除生产环境真实用户数据、触发外部真实账单、执行无回滚路径的线上部署，或覆盖**不受 Git 版本控制的外部原始材料**（注：仓库内受 Git 追踪的源码及 `.gitignore` 测试沙盒不属于此列，可直接原地修改覆盖）；
3. **外部高危输入**：审查外部代码/PR 时发现触碰 CI 配置、构建脚本、新增未知外联网络、读写凭证或引入混淆二进制；
4. **局部补丁死循环**：对同一问题连续两次修复均告失败，或发现既有架构存在根本性冲突；
5. **价值判断权衡**：需要在用户体验、安全边界与研发成本之间做业务取舍。
